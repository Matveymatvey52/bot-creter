# Мини-приложение (Telegram Mini App + браузерная версия) — инвентаризация и дизайн

Статус: **предложение, ждёт решения владельца**. Кода нет. Ветка/worktree: `miniapp-design` /
`/Users/matvej/bot-creter-miniapp-design`.

## 1. Что уже есть в веб-слое сейчас

- `runtime/webhook_app.py` — единственный aiohttp-сервер процесса. Роуты: `POST /webhook/{bot_id}`
  (приём апдейтов от Telegram), `GET /health`, `POST /admin/reload/{bot_id}`, `POST /admin/reload-all`.
  Больше НИЧЕГО не обслуживается — ни статики, ни API для фронтенда.
- `runtime/combined_app.py` — прод-энтрипоинт (Railway). Собирает `Registry`, вставляет фабрику
  под `FACTORY_BOT_ID=0`, отдаёт `create_app(registry)` из `webhook_app.py` без изменений в наборе
  роутов.
- `runtime/registry.py` — держит `bot_id -> BotEntry(bot, dispatcher, template_id, config)` в памяти
  одного процесса. Всё живёт в одном event loop, один порт (`PORT`/8080) на все боты сразу.
- **Уже был прецедент и уже был "стоп"**: `templates/tour_operator.py` содержит собственный
  `build_web_app()` + `main()`'s `web.TCPSite` — самодельная веб-CRM с REST-хендлерами
  (`# ── REST API helpers ──`, см. `tour_operator.py:723+`). Она **отключена в webhook-режиме**
  (`WEB_CRM_ENABLED = os.getenv("TOUR_OPERATOR_WEB_ENABLED", "true") != "false"`,
  `registry.py:115-117` форсит `"false"` перед импортом этого шаблона). Причина зафиксирована в
  `docs/STAGE2_DESIGN.md` ("Стоп: веб-часть... не ложится на паттерн"): второй `web.TCPSite` на тот
  же `PORT` внутри общего `webhook_app.py`-процесса → `OSError: Address already in use` при первом
  же боте на этом шаблоне.

**Вывод: любое мини-приложение обязано жить как ДОПОЛНИТЕЛЬНЫЕ РОУТЫ на существующем aiohttp-сервере
`combined_app.py`, а не как отдельный `web.TCPSite`/процесс на бота.** Это не новое архитектурное
решение — это прямое следствие уже зафиксированного ограничения, и оно снимает главный открытый
вопрос (#2) почти полностью.

## 2. Ответы на 4 вопроса

### 2.1 Технология: Telegram Mini App + браузер — одна кодовая база

**Рекомендация: одна SPA на чистом React (Vite), без тяжёлого мета-фреймворка (Next.js и т.п. не
нужны — нет SSR-потребности, всё за авторизованным API).**

- Telegram Web Apps — это просто веб-страница в WebView с доступом к `window.Telegram.WebApp`
  (init data, тема, `MainButton`, haptics). Та же страница, открытая в обычном Chrome без этого
  объекта, обязана работать как самостоятельный сайт — `window.Telegram?.WebApp` должен быть
  **опциональным слоем**, а не обязательной зависимостью.
- Один билд, два входа авторизации:
  - В Telegram: `Telegram.WebApp.initData` (подписанная строка) отправляется на бэкенд, бэкенд
    проверяет HMAC подписи (стандартная процедура Telegram) → получает `telegram_user_id`.
  - В браузере: логин через Telegram Login Widget либо magic-link из бота (бот при `/app`
    присылает одноразовую ссылку с коротким токеном — паттерн уже почти есть в
    `tour_operator.py`'s `f"{BASE_URL}/app?token={m.from_user.id}"`, только токен там пока что просто
    `user_id` без подписи/срока действия — это НАДО исправить, не копировать как есть).
- Почему не два отдельных фронтенда: разная разметка/логика на два таргета — двойная
  поддержка, дизайн-система (см. §3) неизбежно разъедется. Условная отрисовка одной ветки UI
  ("есть Telegram MainButton → используем его вместо своей нижней кнопки") — единственное реальное
  различие, и это тривиально инкапсулируется в один hook (`useTelegramWebApp()`), не в отдельный билд.

### 2.2 Бэкенд: новые роуты в `combined_app.py`, НЕ отдельный сервис

Расширяем существующий `web.Application` (тот же процесс, тот же `Registry`, тот же порт):

```
GET  /app/{bot_id}                → отдаёт SPA (статика, один index.html на все боты)
GET  /api/{bot_id}/me             → профиль + права (проверка initData/токена)
GET  /api/{bot_id}/<resource>     → список записей (per-template)
GET  /api/{bot_id}/<resource>/{id}→ детали записи
POST /api/{bot_id}/<resource>     → создание записи
```

Ключевое: эти роуты **не знают про конкретный шаблон**. По аналогии с тем, как
`_load_and_include_features()` в `registry.py` подключает `features/*.py` по конвенции
(`router`, `init_db`, `bot_commands`), новый слой мини-аппа должен подключать
**`miniapp_config` по конвенции** из template-модуля: каждый шаблон, который хочет мини-апп,
экспортирует декларативную схему данных (какие ресурсы показывать, какие поля, какие статусы) —
не HTML/JS, а конфиг. Общий REST-хендлер в новом `runtime/miniapp_api.py` (тот же паттерн, что
`webhook_app.py`) читает эту схему и обслуживает CRUD против того же `config.db_path`, которым уже
пользуется сам шаблон через aiosqlite.

Авторизация переиспользует то, что уже есть: `WEBHOOK_SECRET`-подобная fail-closed проверка для
админских операций, HMAC-проверка `initData` для обычных пользователей — никакой новой секретной
инфраструктуры, тот же `hmac.compare_digest` паттерн, что в `webhook_app.py:56`.

Это прямая параллель уже принятому в проекте паттерну "движок + per-bot конфигурация"
(`features/payments.py` + `features/sellable_items.py`, `features/sheets.py`) — тот же принцип
масштабируется на веб-слой.

### 2.3 Автогенерация при `/create`: конфиг, не код

**Не генерировать JS/React-код на бота.** Один статический SPA-билд обслуживает ВСЕ боты
(`GET /app/{bot_id}` — `bot_id` только определяет, какие данные подтягивать через API, но не какой
код грузится). Новый бот получает мини-апп бесплатно, если:

1. Шаблон, который выбрал `_select_template`/`generate_bot_code`, экспортирует `miniapp_config`
   (декларативный dict: ресурсы, поля, статусы, лейблы — аналог того, что уже делает
   `config_from_bot_row` для типизированного конфига).
2. При кастомизации через `_customize_from_template`/`_synthesize_from_templates` Claude
   **не трогает мини-апп вообще** — эти функции работают с Python-кодом бота, `miniapp_config`
   либо наследуется как есть из референс-шаблона (для 1-template customize), либо генерируется
   отдельным явным шагом (для synthesis/from-scratch режимов, где схема данных реально новая).

Практически: добавить в пайплайн `generate_bot_code()` (`services/claude_service.py:1534`) один
дополнительный шаг ПОСЛЕ того, как код бота готов и прошёл ревью — короткий, дешёвый Claude-вызов
"опиши экраны мини-аппа как JSON-схему по этому коду бота" (аналог `classify_bot_type`, не
аналог тяжёлой генерации кода: 1-2K токенов, не 25K). Если шаг падает/даёт невалидный JSON — бот
просто не получает мини-апп (деградация до чисто Telegram-бота, как сейчас), ничего не блокирует
создание бота.

Итог: разработчик НЕ трогает фронтенд руками на каждый новый шаблон. Новый шаблон = Python-файл с
опциональным `miniapp_config` (как уже сегодня новый шаблон = Python-файл с опциональным
`router`/`init_db`).

### 2.4 Масштаб первого шага: один pilot-шаблон, вручную, БЕЗ автогенерации на этом этапе

Автогенерация конфига (§2.3, шаг 4) — это Phase 2, после того как ручной pilot докажет, что сама
схема "движок + конфиг" вообще покрывает реальные данные бота без костылей.

**Pilot-кандидат: `tour_operator`.** Не случайно — это ЕДИНСТВЕННЫЙ шаблон, где владелец уже явно
хотел веб-интерфейс (собственная insta-CRM в `main()`) и где есть готовый, проверенный на реальных
требованиях набор экранов (туры → секции ЛиП/отели/гости/ДДС). Взять существующую бизнес-логику
tour_operator.py (`_section_summary`, REST-хендлеры) как источник правды для первой `miniapp_config`,
но реализовать её через ОБЩИЙ движок, а не оживлять старый `build_web_app()`.

Альтернатива на случай, если владелец предпочтёт более простой pilot: `sellable_items` +
`orders_tracker` — проще по данным (один ресурс: список позиций/заказов), но менее показательно,
раз там нет реального прежде существовавшего веб-опыта для сравнения.

## 3. Дизайн-система (единая, не переизобретать на шаблон)

Тёмная тема + фиолетовый акцент + крупные скруглённые карточки — фиксируется как ОДИН набор CSS-
токенов (`--bg`, `--surface`, `--accent`, `--radius-lg` и т.п.) в общем SPA, не как per-template
стиль. Любой шаблон с `miniapp_config` автоматически выглядит consistent, потому что верстают
компонент-библиотека и `miniapp_config`-schema, а не HTML на шаблон.

### 3.1 Конкретная спецификация по скриншотам quicon.space (владелец подтвердил: "наш дизайн должен быть похож")

Токены (значения — отправная точка для CSS, финальные хексы уточнить при вёрстке):

| Токен | Значение | Где видно на скриншотах |
|---|---|---|
| `--bg` | почти чёрный (`#0d0d10`–`#111114`), НЕ чистый `#000` | фон всего экрана |
| `--surface` | чуть светлее фона (`#1a1a1f`–`#1e1e24`), едва отличим от `--bg` | карточки, модалка "Привязка аккаунтов" |
| `--surface-inset` | ещё чуть светлее `--surface` | pill-чипы метаданных внутри карточки ("каждые 2 ч", "Видео · 7") |
| `--accent` | фиолетовый (`#7c5cff`–`#8b6cff`) | primary-кнопка "Сгенерировать", активная вкладка-переключатель вида, "+" кнопка, чекбоксы, активный таб "Основные" |
| `--accent-text` | белый на `--accent` | текст на фиолетовой кнопке |
| `--success` | зелёный, приглушённый (`#1e3a2f` фон / `#4ade80` текст) | бейдж статуса "АКТИВЕН" |
| `--text-primary` | почти белый | заголовки карточек |
| `--text-secondary` | серый (`#8a8a94`) | второстепенный текст ("след: через 29 мин", даты) |
| `--radius-lg` | ~16–20px | карточки, модалки, поле поиска |
| `--radius-pill` | 999px (полное скругление) | чипы, кнопка "+", бейдж статуса |

Паттерны компонентов, видимые на скриншотах:
- **Карточка списка**: заголовок сверху слева + статус-бейдж справа (зелёная pill), ниже ряд(ы)
  pill-чипов с метаданными (иконка + текст), затем блок "участников"/тегов с аватарками, снизу —
  ряд с полем ввода числа + одна широкая primary-кнопка (фиолетовая, с иконкой), в самом низу —
  тонкая линия-разделитель и мета-строка ("обновлён ...") с меню из трёх точек справа.
- **Переключатель вида** (grid/list/table): группа pill-кнопок вверху экрана, активная — залита
  `--accent`, неактивные — `--surface-inset` с серой иконкой.
- **Модалка/нижний лист** ("Привязка аккаунтов"): всплывает поверх с затемнением фона, заголовок +
  подзаголовок сверху, поле поиска (`--radius-lg`, `--surface-inset`), фильтр-чипы под ним,
  список выбираемых строк с чекбоксом слева (залит `--accent`, галочка белая) — каждая строка сама
  как мини-карточка со скруглением и тонкой фиолетовой обводкой, когда выбрана. Снизу модалки —
  панель с "Выбрано: N" и двумя кнопками (вторичная "Отмена" — просто текст/обводка, primary
  "Сохранить" — залитая `--accent`).
- **Форма редактирования** (полноэкранная, не модалка): шапка с крестиком-закрыть слева, заголовком
  по центру-слева, кнопкой "Сохранить" справа (залитая `--accent`, компактная). Табы под шапкой —
  подчёркивание активного таба цветом `--accent`, неактивные — просто серый текст без фона. Внутри —
  toggle-свитчи (залиты `--accent` во включённом состоянии) с заголовком + серым описанием под ним;
  раскрывающиеся секции ("Сцена 1", "Сцена 2") как отдельные карточки с action-иконками (▲▼✕) справа
  от заголовка секции.

Явно НЕ то, что нужно: никаких неоновых градиентов, стеклянных блюров, 3D-элементов или "Web3"
эстетики (crypto-style свечения, частицы и т.п.) — только плоские залитые поверхности, чёткие
границы через разницу яркости фона/карточки, минимум декоративных эффектов. Это подтверждено
явным пожеланием владельца в §0 (описание задачи) и визуально — на референс-скриншотах нет ни
одного blur/shadow/gradient эффекта, только плоский цвет + типографика + скругления.

Три типа экрана из §3.2 ниже (список/детали/форма) строятся именно на этих трёх паттернах:
карточка-списка → карточка-деталей (тот же паттерн карточки, развёрнутый) → полноэкранная форма
редактирования (третий паттерн, но без табов — pilot не нуждается в них).

### 3.2 Референс-паттерн экрана (общий, из исходных скриншотов kupikod.com/quicon.space)
заголовок → теги/статус-чипы → список крупных карточек → одна primary-кнопка снизу (не панель
из мелких кнопок). Три типа экрана достаточно для pilot:

1. **Список** — карточки записей (заявка/тур/заказ), статус-чип, тап → детали.
2. **Детали одной записи** — крупная карточка с полями + история/секции, primary-кнопка действия
   снизу (например "Отметить оплаченным").
3. **Форма создания** — минимум полей, одна primary-кнопка "Создать" снизу (Telegram `MainButton`
   в Mini App-контексте, обычная fixed-кнопка в браузере).

## 4. Статус реализации (pilot, tour_operator)

Владелец подтвердил pilot (`tour_operator`) и архитектуру "1 SPA-движок + декларативный
`miniapp_config`" — работа продолжена без дальнейших стопов, см. историю коммитов на ветке
`miniapp-design`.

Реализовано:
- **Бэкенд**: `runtime/miniapp_api.py` — CRUD REST-слой (`/api/{bot_id}/me`,
  `/api/{bot_id}/{resource}[/{item_id}]`) поверх того же aiohttp-процесса, что и вебхук; двойная
  авторизация (Telegram `initData` HMAC + подписанный истекающий magic-link токен); зарегистрирован
  в `runtime/combined_app.py`.
- **`templates/tour_operator.py`**: `miniapp_config` с ресурсами `tours`/`guests`; `/app`-команда и
  связанные callback-хендлеры теперь шлют подписанный `mint_magic_link_token`-токен вместо старого
  голого `user_id`.
- **Фронтенд**: `miniapp/` — Vite + React + TypeScript SPA. Дизайн-токены из §3.1 в
  `src/index.css`; переиспользуемые компоненты (`Card`, `Chip`, `Badge`) в `src/components/`;
  опциональный слой `window.Telegram.WebApp` в `src/lib/telegram.ts` (везде `?.`, ничего не
  предполагает наличие Telegram-контекста); API-клиент `src/lib/api.ts`, зеркалящий контракт
  `miniapp_api.py`; три типа экрана (`ListScreen`/`DetailScreen`/`CreateFormScreen`) для pilot-
  ресурсов `tours`/`guests`.
- **Раздача статики**: `GET /app/{bot_id}` отдаёт собранный `miniapp/dist/index.html` (после
  проверки, что бот существует и имеет `miniapp_config` — то же самое разграничение, что и у
  `/api/*`); JS/CSS/favicon раздаются под фиксированным префиксом `/app-assets/` (см.
  `miniapp/vite.config.ts`'s `base: '/app-assets/'` — абсолютный, не относительный путь, чтобы
  ссылки на ассеты не зависели от того, под каким `bot_id` была загружена страница).

### 4.1 Важно для деплоя (не забыть)

**ЗАКРЫТО: сборка SPA прописана в Railway build pipeline через `nixpacks.toml`.**

`GET /app/{bot_id}` отдаёт 503, если `miniapp/dist/` не существует. Добавлен `nixpacks.toml` в
корне репо с отдельной фазой `miniapp_build` (`cd miniapp && npm install && npm run build`),
которая выполняется до фазы `install` (Python-зависимости) и до `start` (`bash start.sh`) —
Nixpacks строит граф фаз по `dependsOn`, так что `dist/` гарантированно существует к моменту
старта Python-приложения. `miniapp/node_modules/` и `miniapp/dist/` остаются в `.gitignore`
(регенерируемые артефакты, не коммитятся) — на свежем чекауте их нет, но build step их создаёт
до запуска сервера.

Протестировано локально: чистый `miniapp/dist/` + `node_modules/` удалены, прогнан build step
(`npm install && npm run build` — тот же, что в `nixpacks.toml`), `dist/` появился
(`index.html`, `assets/*.js`, `assets/*.css`), `GET /app/{bot_id}` (напрямую через
`serve_app_shell`, dist не замокан) вернул 200 с реальным `index.html` вместо 503. Полный
regression-прогон `tests/test_miniapp_api.py` (22 теста, включая `test_missing_dist_dir_returns_503`
и app-shell тесты) зелёный.

`services/claude_service.py:1534` — `generate_bot_code()` имеет три ветки (1-template customize,
2-template synthesis, from-scratch), но все три СХОДЯТСЯ в одну точку: в конце у каждой ветки уже
готов финальный, отревьюженный Python-код бота (`code`, после `_review_bot_code`/
`_review_narrow_risk_code`). Это единственное разумное место для нового шага — все три пути дают
на выходе один и тот же артефакт (полный текст `.py`-файла бота с его `init_db()` и
`CREATE TABLE`), так что шаг можно написать один раз и вызвать после `return`-точки каждой ветки
(или, чище, обернуть все три `return` в один хвост функции — `code = await generate_bot_code(...)`
→ `miniapp_cfg = await _generate_miniapp_config(code, requirements_summary)` перед финальным
`return code, miniapp_cfg` или отдельным полем).

Важно: **этот шаг не имеет отношения к `_customize_from_template`/`_synthesize_from_templates`
напрямую** — они остаются как есть (см. §2.3, второй пункт: для 1-template customize, если
референс-шаблон уже несёт `miniapp_config` в своём исходнике, он и так копируется вместе с
остальным кодом шаблона безо всякого доп. шага — Claude, кастомизируя `tour_operator.py`, либо
сохраняет `miniapp_config`-словарь как есть, либо адаптирует его вместе с остальным кодом, это
часть обычной customize-задачи, не отдельный вызов). Новый шаг из этого раздела нужен **только
там, где `miniapp_config` не унаследован от референс-шаблона** — то есть у synthesis (два шаблона
слиты, набор ресурсов мог измениться) и у from-scratch (нет референс-шаблона вообще, схема
целиком новая). На практике проще и надёжнее не различать эти случаи в коде, а всегда запускать
шаг §6.2 над финальным кодом бота (он уже содержит унаследованный конфиг как есть, если он там
есть, и генерация "с нуля по коду" в норме воспроизведёт то же самое, раз код тот же) — но если
экономия токенов на 1-template пути важна, можно добавить дешёвую проверку "уже есть
`miniapp_config = {` в коде → пропустить шаг" перед вызовом.

### 6.2 Механизм: короткий Claude-вызов, вход — код бота + few-shot

Прямая аналогия с `classify_bot_type()` (`services/claude_service.py:805`) — маленький, дешёвый,
narrow-purpose вызов, не полноценная генерация:

```python
async def _generate_miniapp_config(bot_code: str, requirements_summary: str) -> dict | None:
    response = await client.messages.create(
        model="claude-haiku-4-5-20251001",   # не sonnet — narrow JSON-extraction задача
        max_tokens=1500,
        system=MINIAPP_CONFIG_SYSTEM_PROMPT,  # содержит few-shot: tour_operator.py's miniapp_config
        messages=[{"role": "user", "content": f"Bot code:\n\n{bot_code}\n\nRequirements:\n{requirements_summary}"}],
    )
    return _parse_miniapp_config(response.content[0].text)  # best-effort, никогда не raises
```

Вход:
- **Полный код бота** (тот, что уже сгенерирован) — оттуда Claude читает реальные `CREATE TABLE`
  в `init_db()` и берёт **точные имена таблиц/колонок**, не придумывает свои. Это то же самое,
  что уже написано человеком-разработчиком в `tour_operator.py`'s `miniapp_config` (§2 doc-comment
  там прямо говорит: `table` и `field.name` обязаны совпадать с `CREATE TABLE`-колонками) — Claude
  делает ровно ту же работу сверки, что делал бы разработчик руками.
- **`requirements_summary`** — для контекста, какие сущности вообще пользователю показывать
  (не каждая таблица в БД обязана быть ресурсом мини-аппа — например, служебные `admins`/`state`-
  таблицы не нужны в UI).

Промпт (few-shot):
- Show ровно tour_operator.py's `miniapp_config` dict (готовый пример, уже в кодовой базе) как
  единственный образец формата — "вот один правильный пример на реальном шаблоне, сделай такой же
  для этого нового бота".
- Explicit schema constraints: `resources[].table`/`fields[].name` MUST match a real
  `CREATE TABLE`/column in the given code verbatim; no invented tables; `creatable`/`required`
  boolean per field; output ONLY JSON, no markdown fences (тот же паттерн, что и
  `CONNECT_FEATURE_CLASSIFY_PROMPT` в этом же файле — "Respond with ONLY a single line of valid
  JSON").
- Явно сказать: если у бота нет ни одной пользовательской сущности, достойной отдельного экрана
  (например, чисто разговорный бот без БД-таблиц с записями) — вернуть `{"resources": []}` или
  `null`, это ВАЛИДНЫЙ ответ, не ошибка.

### 6.3 Graceful degradation — уже согласованный принцип, применяется буквально

Если шаг падает (сетевая ошибка, timeout, невалидный JSON, JSON не проходит валидацию против
реальных таблиц кода) — **бот всё равно создаётся**, просто без `miniapp_config`. Конкретно:

- `_parse_miniapp_config()` — best-effort парсер по образцу уже существующего
  `_parse_connect_feature_intent()` (`services/claude_service.py:842`, docstring которого прямо
  формулирует этот принцип: "a parsing hiccup here must fall back... never raises") — любая
  проблема (не-JSON, отсутствующие поля, таблица/колонка не найдена в коде бота) → возвращает
  `None`, не бросает исключение.
- Валидация **после** парсинга, до сохранения: для каждого `resources[].table`/`fields[].name` из
  ответа Claude — простая строковая проверка, что такое имя реально фигурирует в `CREATE TABLE ...`
  внутри `bot_code` (regex или `ast`-разбор `init_db()` не нужен, это уже страховка от галлюцинаций
  Claude — не защита от инъекции, `miniapp_api.py` и так трактует конфиг как доверенные
  идентификаторы, см. `tour_operator.py:69-72` doc-comment). Если хоть одно имя не совпадает — весь
  конфиг отбрасывается целиком (не "почини частично"), `miniapp_config = None`.
- Если `_generate_miniapp_config()` вернула `None` — код бота сохраняется как обычно, просто без
  строки `miniapp_config = {...}` в файле. `runtime/miniapp_api.py`'s существующая проверка (уже
  реализована в pilot: `GET /app/{bot_id}` даёт 404/503 если у бота нет `miniapp_config`) уже
  корректно деградирует до "бот работает только как Telegram-бот, без мини-аппа" — это ровно то
  же поведение, что и у любого текущего шаблона без `miniapp_config` сегодня. Ничего нового
  писать в `miniapp_api.py`/`registry.py` для деградации не нужно — оно уже так работает.
- Этот шаг **не должен** быть частью существующих ревью-проходов (`_review_bot_code` и т.п.) —
  если он падает, это не должно триггерить их retry/fix-логику или блокировать сохранение бота.

### 6.4 Стоимость

- Модель: **Haiku**, не Sonnet — задача узкая (JSON-экстракция схемы по уже написанному коду), не
  генерация нового кода. Прямая аналогия — `classify_bot_type()` уже использует Haiku с
  `max_tokens=10` для похожей по духу narrow-классификации.
- `max_tokens` ≈ 1000–1500 (typical `miniapp_config` — 2 ресурса × 5-7 полей, как pilot,
  сериализуется в JSON на несколько сотен токенов; запас на боты с 3-4 ресурсами).
- Input — полный код бота (уже есть в памяти, не доп. чтение с диска) + короткий few-shot
  промпт (~300-500 токенов на сам `tour_operator.py`'s `miniapp_config`-пример) + system prompt.
  Даже для крупного сгенерированного бота (несколько тысяч токенов кода) это несравнимо дешевле,
  чем сама генерация бота (`max_tokens=25000` у `generate_bot_code`'s from-scratch ветки, плюс
  несколько review-проходов поверх) — данный шаг на порядок дешевле каждого из них по стоимости
  и на 1 доп. вызов по времени (~1-3 сек Haiku-latency), не блокирующий по архитектуре (можно
  запускать после того, как бот уже показан владельцу как готовый, если нужно скрыть эту
  задержку — TODO для реализации, не для этого документа).
- Итог: разовая стоимость на бота — доли цента, на 1-2 порядка дешевле генерации самого бота;
  не требует отдельного бюджетирования.

### 6.5 Что осталось нерешённым (для следующего шага, не для этого документа)

- Куда физически писать `miniapp_config`, полученный из этого шага — вставить как Python-словарь
  прямо в текст сгенерированного `.py`-файла бота (симметрично ручным шаблонам, единообразно с
  тем, как `tour_operator.py` уже это делает) или хранить отдельно (например, в БД фабрики рядом
  с остальными метаданными бота, `config_from_bot_row`-стиль)? У обоих вариантов есть
  последствия для `runtime/registry.py` (откуда `miniapp_api.py` сегодня читает конфиг —
  импортом `template_module.miniapp_config`, что предполагает "в коде") — нужно решение владельца,
  не техническая мелочь.
- Нужна ли ревалидация/регенерация `miniapp_config`, если бот позже правится через
  `custom_features` (§ "custom_features" в этом же `claude_service.py`) и меняет схему БД? Не
  покрыто ни pilot'ом, ни этим разделом.
