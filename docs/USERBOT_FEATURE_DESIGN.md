# Дизайн: `channel_monitor` как feature-модуль (а не отдельный юзербот-продукт)

> **УСТАРЕЛО (2026-08-21).** Владелец развернул решение обратно: мониторинг каналов
> снова только отдельный тип бота — `templates/channel_aggregator.py` (см.
> [docs/CHANNEL_AGGREGATOR_TEMPLATE_DESIGN.md](CHANNEL_AGGREGATOR_TEMPLATE_DESIGN.md)).
> `features/channel_monitor.py` физически остался в репозитории (не удалён) только
> ради уже существующего бота 12 (tour_operator_demo), у которого фича была включена
> до этого решения — `COMPATIBLE_WITH` сужен до `channel_aggregator`, конструктор
> больше не предлагает её как опцию для новых ботов любого другого шаблона. Документ
> ниже описывает дизайн, который теперь отменён, оставлен для истории.

Продолжение [docs/CHANNEL_MONITOR_DESIGN.md](CHANNEL_MONITOR_DESIGN.md) (отклонённый Bot-API-вариант)
и [docs/USERBOT_CHANNEL_MONITOR_DESIGN.md](USERBOT_CHANNEL_MONITOR_DESIGN.md) (принятая Telethon-архитектура,
но как **отдельный standalone-продукт** `templates/channel_monitor.py`). Новое требование владельца:
это должна быть **фича, которую можно включить любому боту фабрики** — по образцу `features/payments.py`,
`features/sheets.py`, `features/office_events.py` — а не отдельная жёстко заданная сущность.

**Это дизайн-документ. Кода нет. Стоп в конце — обязательно дождаться подтверждения.**

## 0. Что переносится из предыдущего дизайна без изменений

Из [USERBOT_CHANNEL_MONITOR_DESIGN.md](USERBOT_CHANNEL_MONITOR_DESIGN.md) остаются верными и не
переосмысливаются здесь:
- §1 — хранение сессии: `StringSession`, Fernet-шифрование, отдельный `USERBOT_ENCRYPTION_KEY`.
- §3 — процессная модель: отдельный Railway-сервис `userbot-worker`, мультиплексирование клиентов
  в одном asyncio-процессе, restart/recovery по `status='active'`.
- §5 — точка интеграции Gemini: только текст постов, отдельный `services/gemini_service.py`.
- §6 — текст рисков перед первым запросом номера телефона.
- Ограничение Telegram (юзербот видит только каналы, куда сам аккаунт вступил) — актуально
  одинаково для ЛЮБОГО бота фабрики, это свойство Client API, а не свойство конкретного шаблона
  (см. §5 ниже).

Что меняется — везде, где предыдущий дизайн предполагал `templates/channel_monitor.py` как
самостоятельный продукт с собственным `/start`, тот код превращается в `features/channel_monitor.py`,
подключаемый к УЖЕ существующему боту через тот же механизм, что `payments`/`sheets`/`office_events`.

## 1. Что значит "любой бот фабрики может стать юзерботом"

Ключевое архитектурное решение: юзербот-сессия (Telethon `StringSession`) авторизуется **владельцем
бота**, а не привязана к конкретному `template_id`. Технически включение фичи `channel_monitor` для
бота X означает:

1. В `bot_features` для `bot_id=X` появляется строка `channel_monitor` (тот же механизм toggle, что
   уже есть для `payments`/`sheets` — `feature-modules system`, влито в master).
2. Бот X получает дополнительные хендлеры (роутер фичи, склеенный тем же `_clone_router` +
   `_attach_bot_id_middleware` паттерном, что и остальные фичи) — в частности новую команду/кнопку
   «📡 Мониторинг каналов» в своём обычном меню.
3. Через эту кнопку владелец бота X проходит FSM авторизации Telethon-аккаунта (см. §2
   предыдущего дизайна, без изменений) — тот самый диалог "номер телефона → код → 2FA".
4. Полученная `userbot_sessions` запись привязана к `(owner_user_id, bot_id)`, не только к
   `owner_user_id` — см. §2 ниже, почему это важно.

Итог: НЕТ отдельного продукта-юзербота. ЕСТЬ опция в конструкторе бота "включить фичу
'Мониторинг каналов'", как любая другая фича, применимая к списку совместимых шаблонов.

## 2. Привязка сессии: к боту или к владельцу?

Открытый архитектурный вопрос, требующий решения владельца (см. §6 — открытые вопросы).
Два варианта:

**Вариант A — сессия привязана к `bot_id`** (одна Telegram-сессия на один бот фабрики):
```sql
CREATE TABLE userbot_sessions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    bot_id INTEGER NOT NULL,              -- FK -> bots.id, НЕ owner_user_id
    owner_user_id INTEGER NOT NULL,       -- кто ввёл номер (для аудита/уведомлений)
    phone TEXT NOT NULL,
    session_string TEXT,
    status TEXT DEFAULT 'pending',
    created_at TEXT DEFAULT (datetime('now','localtime')),
    updated_at TEXT DEFAULT (datetime('now','localtime'))
);
```
- Изоляция полная: у бота A и бота B — разные Telegram-аккаунты-юзерботы, даже если ими управляет
  один и тот же владелец фабрики. Просто и предсказуемо, ложится один-в-один на существующий
  паттерн "данные фичи живут в `db_path` конкретного бота" (feature-modules-inventory: "features
  intentionally reuse the host template's own per-bot db_path").
- Минус: если владелец хочет мониторить каналы одним и тем же личным Telegram-аккаунтом из
  нескольких своих ботов фабрики — придётся проходить полную FSM-авторизацию заново для каждого
  бота, даже с тем же номером телефона.

**Вариант B — общий пул сессий на владельца** (как в предыдущем standalone-дизайне, §1: таблица
в центральной БД фабрики, `owner_user_id` без `bot_id`):
- Один раз авторизовал номер — можно переиспользовать в нескольких ботах фабрики, каждый со своим
  списком `monitored_channels`/`channel_posts` (эти таблицы остаются per-`bot_id`, привязка к
  сессии — только по `owner_user_id`).
- Минус: сложнее модель прав — что если владелец хочет отозвать доступ у бота A, не трогая бота B,
  использующего тот же Telegram-аккаунт? Нужна отдельная таблица связки `bot_id ↔ session_id`
  (многие-ко-многим), а не прямая колонка.
- Минус: `userbot-worker` должен резолвить "какие каналы льются в какого бота" по паре
  `(session_id, bot_id)`, а не просто по `session_id` — усложняет и §4 (сбор постов), и revoke-логику.

Рекомендация ниже в §6 — вариант A как более простой и согласованный с существующим паттерном
"фича = данные в `db_path` этого бота", но это решение владельца, не техническая необходимость.

## 3. Feature-модуль: структура, COMPATIBLE_WITH

`features/channel_monitor.py` по образцу `features/payments.py`/`features/office_events.py`:

```python
# FEATURE: channel_monitor
# COMPATIBLE_WITH: accountant, campaign_tracker, manager_secretary, ... (см. ниже)
```

**Router** — тот же набор хендлеров, что был в `templates/channel_monitor.py`
(cmd_start-эквивалент **убирается** — фича не владеет `/start` бота, только добавляет кнопку/команду
в существующее меню хоста), включая:
- `UserbotAuthStates` FSM (риск-экран → телефон → код → 2FA).
- Панель "📋 Мои каналы" / "📰 Лента" / toggle канала.
- `/disconnect`-эквивалент (revoke сессии).

**`init_db(db_path)`** — создаёт `monitored_channels`/`channel_posts` в `db_path` ЭТОГО бота
(тот же паттерн, что `payments.py init_db` создаёт свои таблицы в per-bot БД) — эти таблицы
**остаются per-bot** независимо от решения по §2, потому что лента/список каналов — это то, что
видит конкретный бот, а не общая сущность фабрики.

**`bot_commands`** — фича объявляет `[("monitor", "Мониторинг каналов")]`, попадает в общий
`set_my_commands()` вызов вместе с командами других включённых фич этого бота (существующий
механизм из `_load_and_include_features` в `runtime/registry.py`, без изменений).

**COMPATIBLE_WITH — не "*":** в отличие от `notifications.py` (`COMPATIBLE_WITH: *`, потому что
уведомления универсальны для любого бота), `channel_monitor` предполагает содержательный смысл
только там, где лента чужих постов полезна владельцу бота — рабочая гипотеза списка (стоит
отметить: `features/sales_analytics.py:2` уже включает `channel_monitor` в СВОЙ
`COMPATIBLE_WITH`-список как ЦЕЛЕВОЙ шаблон — это оставшийся след старого standalone-дизайна,
где `channel_monitor` был отдельным template_id; при переходе на feature-модуль эту строку в
`sales_analytics.py` тоже нужно будет пересмотреть, т.к. `channel_monitor` перестаёт быть
template_id и не может больше стоять в списке шаблонов): `accountant, campaign_tracker,
manager_secretary, tour_operator, boss_bot, manager_bot` и далее по решению владельца — список
утверждается отдельно, не блокирует остальной дизайн.

## 4. FSM авторизации — без изменений по механике, с одним отличием

Диалог (§2 предыдущего дизайна: риск-экран → телефон → код → опционально 2FA → успех) переносится
как есть. Отличие только в ТОЧКЕ ВХОДА: раньше это был `cmd_start` самостоятельного бота, теперь —
кнопка «📡 Мониторинг каналов» в существующем меню бота-хоста (владелец фабрики уже требует кнопки
вместо текстовых команд везде — существующее правило дизайна UI, не противоречит).

Risk-текст (§6 предыдущего дизайна) показывается один раз при первом входе в FSM конкретно для
ЭТОГО бота (если решение по §2 — вариант A, отдельная сессия на бота — то и риск-подтверждение
логично запрашивать заново на каждый бот, т.к. это новая авторизация нового Telegram-аккаунта
с точки зрения этого бота, даже если технически тот же номер уже где-то авторизован).

## 5. Ограничение Telegram — одинаково для любого бота-хоста

Ограничение Client API (юзербот видит только каналы, куда сам аккаунт УЖЕ вступил как обычный
пользователь) не зависит от того, какой шаблон фабрики фичу подключил — это свойство самого
Telegram-аккаунта, авторизованного через Telethon, а не свойство бота-хоста. Следствия:

- «➕ Добавить канал» пытается `client.get_entity(username)` + `JoinChannelRequest` — работает
  для публичных каналов одинаково независимо от бота-хоста (§4 предыдущего дизайна, без изменений).
- Приватные каналы (invite-only, куда аккаунт ещё не приглашён) — тот же явный отказ с объяснением,
  без изменений, независимо от бота-хоста.
- Если владелец хочет мониторить канал, куда его юзербот-аккаунт УЖЕ состоит участником (вступил
  вручную, не через фичу) — тоже работает одинаково: `get_entity` находит канал, `JoinChannelRequest`
  на уже-состоящем аккаунте — no-op/успех, канал добавляется в `monitored_channels`.

Это ограничение стоит показать явно и в тексте фичи при подключении (переиспользуя RISK_TEXT из
`templates/channel_monitor.py:56-69`, слово в слово, т.к. текст уже одобрен и не завязан на
конкретный бот-хост).

## 6. Открытые вопросы — нужно решение владельца перед реализацией

1. **§2 — привязка сессии**: вариант A (сессия на бота, проще, изоляция по умолчанию) или
   вариант B (пул на владельца, сложнее, но переиспользование одного номера телефона между
   несколькими ботами фабрики). Рекомендация: **вариант A** — совпадает с существующим паттерном
   "данные фичи — per-bot", не требует новой таблицы связки многие-ко-многим, и отзыв доступа
   у одного бота не задевает остальные автоматически.
2. **`COMPATIBLE_WITH`-список**: какие именно шаблоны получают эту фичу в UI конструктора —
   и отдельно: нужно ли править `features/sales_analytics.py:2`, убирая устаревшее упоминание
   `channel_monitor` как шаблона (см. §3)?
3. **`userbot-worker` — общий сервис на всю фабрику или намёк на будущий шардинг сразу**:
   §3 предыдущего дизайна предполагал один сервис для (тогда) одного продукта. Теперь потенциально
   МНОГО ботов включают фичу — нужно подтвердить, что один `userbot-worker`-процесс,
   мультиплексирующий все Telethon-клиенты всех ботов фабрики разом, — это по-прежнему приемлемый
   старт (а не сразу шардинг), учитывая что теперь количество активных клиентов может расти быстрее.
4. **Судьба `templates/channel_monitor.py`**: удаляется полностью (заменяется фичей) или остаётся
   как отдельный standalone-шаблон ДЛЯ ТЕХ, кто хочет бота, целиком посвящённого мониторингу —
   и фича добавляется ДОПОЛНИТЕЛЬНО для остальных? (Дублирование логики между `templates/` и
   `features/` версией — сознательный выбор или технический долг, если оставить оба?)
5. **`USERBOT_ENCRYPTION_KEY` и `TELEGRAM_API_ID`/`TELEGRAM_API_HASH`**: остаются одни на всю
   фабрику (значит все юзербот-сессии всех ботов используют один и тот же зарегистрированный
   Telegram-application `api_id`/`api_hash`) — подтверждение, что это осознанно и не требует
   per-owner своего `api_id` (что было бы отдельной, более сложной моделью).

## 7. Стоп

Дизайн переносит принятую Telethon-архитектуру (хранение сессии, FSM, процессная модель, Gemini,
риски — из `USERBOT_CHANNEL_MONITOR_DESIGN.md`) в форму feature-модуля, подключаемого к любому
совместимому боту фабрики через существующий `bot_features`/`discover_features`/`COMPATIBLE_WITH`
механизм — вместо отдельного standalone-продукта. Открыты 5 вопросов (§6), решение по ним
(особенно §2 — привязка сессии) определяет финальную схему БД и объём работы по revoke-логике.

Кода нет — это дизайн-этап. Жду подтверждения от владельца перед реализацией.
