# ТЗ: модель аудитории бота (для кого этот бот)

**Дата:** 2026-08-22
**Постановщик:** владелец
**Статус:** к исполнению отдельной сессией

---

## 1. Проблема

Мини-апп показывает владельцу тур-оператора **две вкладки «Туры»**. Это не дефект
вёрстки — это дефект конфига. В `templates/tour_operator.py` объявлены два
ресурса на одной и той же таблице `tours`:

| Ресурс | Таблица | Заголовок | role_filter | children |
|---|---|---|---|---|
| `tours` | `tours` | Туры | нет | да |
| `tours_public` | `tours` | Туры | да | нет |

Замысел был такой: `tours` — для админа, `tours_public` — урезанный вид для
клиента. Владелец проходит оба фильтра и видит **оба**.

Но у этого бота клиентов нет вообще. Тур-оператор — инструмент **одного
человека**: владелец ведёт свои туры, гостей и деньги. Отдельный «клиентский»
срез здесь не нужен ни в каком виде, и вопрос владельца «зачем мне смотреть
чужие туры» поставлен верно — смотреть нечего, второй ресурс существует впустую
и только плодит дубли во вкладках и в нижней навигации.

**Корень проблемы шире одного шаблона: у бота нигде не записано, для кого он.**
Каждый шаблон решает это по-своему и молча, поэтому:

- одни шаблоны городят клиентские дубли там, где клиентов нет;
- другие, наоборот, рискуют показать клиенту админские разделы, потому что
  автор шаблона про это не подумал;
- генератор конфигов (`services/claude_service.py`) не спрашивает и не знает,
  какая у бота аудитория, и воспроизводит ту же кашу в новых ботах.

## 2. Две модели, которые нужно различать

**А. Однопользовательский бот (owner_only).**
Весь бот — рабочий инструмент владельца. Других ролей нет. Все разделы
принадлежат ему, `role_filter` не нужен, клиентских дублей быть не должно.
Примеры: тур-оператор, учёт расходов, трекер привычек, ежедневник.

**Б. Двухаудиторный бот (owner_and_clients).**
У бота есть владелец/админ и внешние пользователи, и они видят **разное**: админ
заводит товары, услуги, расписание; клиент выбирает, бронирует, покупает и видит
только своё. Здесь `role_filter` осмыслен и обязателен.
Примеры: магазин, запись в салон/клинику/фитнес, доставка, приём заявок.

Сейчас различие существует только в голове автора шаблона. Его нужно сделать
**явным и проверяемым**.

## 3. Что сделать

### 3.1. Объявить аудиторию в конфиге

Ввести в `miniapp_config` поле верхнего уровня:

```python
miniapp_config = {
    "audience": "owner_only",   # либо "owner_and_clients"
    "resources": [...],
}
```

Для `owner_and_clients` каждый ресурс объявляет, кому он виден:

```python
{"name": "orders", "visibleTo": "clients", ...}   # clients | owner | both
```

Значения по умолчанию выбрать так, чтобы конфиги без этих полей продолжали
работать, и это явно описать в коде — в проекте уже принято деградировать
мягко, а не падать.

### 3.2. Провести аудит всех шаблонов

38 шаблонов с `miniapp_config`. По каждому:

1. определить модель (А или Б) по смыслу шаблона, а не по наличию
   `role_filter`;
2. проставить `audience`;
3. **у однопользовательских снести клиентские дубли** — в первую очередь
   `tours_public` в `tour_operator.py`. Перед удалением проверить, не ведёт ли
   на этот ресурс что-то ещё (клиентские ссылки, `services/client_link.py`,
   веб-часть шаблона): если ведёт — сначала распутать, потом удалять;
4. у двухаудиторных — проверить, что клиентские разделы действительно
   ограничены `role_filter`, а админские клиенту не видны.

Результат аудита — таблица «шаблон → модель → что исправлено» в этом файле.

### 3.3. Научить движок

- `runtime/miniapp_api.py`: отдавать `audience` и `visibleTo` в `/schema` и не
  отдавать ресурс, не предназначенный этому зрителю (рядом с уже существующей
  проверкой прав — не вместо неё).
- Мини-апп: не показывать в ленте и в нижней навигации два раздела с
  одинаковым заголовком — страховка от повторения истории.

### 3.4. Закрыть дыру у новых ботов

`MINIAPP_CONFIG_SYSTEM_PROMPT` в `services/claude_service.py`:

- добавить в правила требование определить аудиторию по описанию бота и
  вернуть `audience`;
- прямо запретить создавать два ресурса на одной таблице ради «клиентского
  вида», если бот однопользовательский;
- дополнить few-shot пример обоими случаями.

Плюс валидация в `_parse_miniapp_config`: конфиг без `audience` или с двумя
ресурсами на одной таблице с одинаковым заголовком — отклонять с внятной
причиной, ровно как уже делается для выдуманных таблиц.

### 3.5. Тесты

- регресс: ни один шаблон не объявляет два ресурса на одной таблице с
  одинаковым `title`;
- каждый шаблон объявляет `audience`;
- у `owner_and_clients` каждый клиентский ресурс имеет `role_filter`;
- генератор: конфиг без `audience` отбраковывается.

## 4. Критерии приёмки

1. У тур-оператора одна вкладка «Туры» — и в ленте, и в нижней навигации.
2. Каждый из 38 шаблонов объявляет `audience`; таблица аудита заполнена.
3. Ни одного ресурса-дубля на одной таблице с одинаковым заголовком.
4. Новый бот из описания «инструмент для меня одного» получает `owner_only` и
   ни одного клиентского дубля.
5. Новый бот из описания «магазин с покупателями» получает
   `owner_and_clients`, клиентские разделы под `role_filter`.
6. Полный прогон тестов. Известные предсуществующие падения регрессом не
   считаются, новых нет.

## 5. Чего НЕ делать

- Не трогать утверждённый дизайн варианта I (экраны списка, карточки, создания,
  «Все разделы», вложения) — задача только про то, какие разделы кому видны.
- Не удалять клиентские ресурсы у шаблонов модели Б.
- Не вести это в ветке `scope-context-audit` (пикер родителя) — конфликты по
  файлам шаблонов гарантированы.

  `_validate_miniapp_config_against_code`.
- Отдача схемы: `runtime/miniapp_api.py` — `schema_handler`,
  `_resource_display_schema`, `_SCHEMA_RESOURCE_KEYS`.
- Ролевые фильтры: `docs/MINIAPP_ROLE_SCOPING_DESIGN.md`, `_compile_role_where`.
  Этот документ описывает **механику** фильтров; он не отвечает на вопрос, есть
  ли у бота клиенты вообще — именно эту дыру и закрывает настоящее ТЗ.
- Смежная незакрытая работа, не смешивать: у 38 шаблонов `children` объявлен у
  4, `kind: "file"` — ни у одного, поэтому карточка записи выглядит бедно.
  Файлы те же самые, поэтому очередность согласовать заранее.
