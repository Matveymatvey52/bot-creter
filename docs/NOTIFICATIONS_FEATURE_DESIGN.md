# notifications.py — рассылка от владельца бота: инвентаризация и дизайн

Статус: **дизайн, БЕЗ кода**. Ждёт подтверждения владельца перед реализацией.

## 1. Контракт фич-модуля (из payments.py / sheets.py / office_events.py)

Общее для всех трёх:
- Заголовок `# FEATURE: <name>` + `# COMPATIBLE_WITH: <template_id, template_id, ...>` в первых 10 строках файла — единственное, что парсит `runtime/registry.py`'s `discover_features()`. Список explicit, без сентинела "all" — осознанное решение ("добавление 13-го шаблона не должно тихо сделать его совместимым со всем").
- Модуль-уровневый `router = Router()` (может быть пустым, как у sheets.py — не каждая фича вешает свои хендлеры).
- **Никогда не открывает свою БД.** Данные фичи живут как доп. таблицы в ХОСТ-боте `db_path` (payments.py, `init_payments_tables`) либо в центральной factory-БД `db/database.py` (sheets.py — `bot_sheets_config`; office_events.py — общая шина).
- `init_db(db_path)` — по конвенции читается `runtime/registry.py`'s `build_entry()`/`_load_and_include_features()`, вызывается один раз при регистрации бота.
- Функции принимают `bot_id`/`config` явно от вызывающего кода (host-шаблона), а не тянут их из глобального состояния — тот же паттерн, что `create_invoice(bot, bot_id, ...)`.
- Опционально `bot_commands: list[tuple[str,str]]` — фича может объявить свои команды в общее меню бота (см. `sellable_items.py`), собираются со всех включённых фич и пушатся одним `set_my_commands()`.
- Rate-limit / антиспам НЕ является встроенным примитивом ни у одной существующей фичи — их придётся спроектировать с нуля здесь (Telegram Bot API: ~30 msg/sec суммарно на бота, до 1 msg/sec на конкретный chat_id при broadcast — см. §4).

## 2. Критический архитектурный разрыв: from-scratch боты и COMPATIBLE_WITH

Задача требует: фича должна автоматически работать для **любого** бота, включая from-scratch (без `# TEMPLATE:` маркера, без `templates/<id>.py` модуля). Инвентаризация показала, что сегодня это невозможно без внешних изменений, по ДВУМ независимым причинам:

### 2.1 Разрыв в загрузке (закрывается ПАРАЛЛЕЛЬНОЙ сессией — не трогать)
`_load_and_include_features()` (реально грузит и монтирует роутер фичи) вызывается только если `typed_config is not None`, а `typed_config` требует резолва `template_id` → `templates/<id>.py` модуль. From-scratch бот (`module is None`) сегодня **вообще не получает фич**, даже если бы `COMPATIBLE_WITH` его разрешал (тот же гэп, что у `office_events`' "Custom-бот scope").

**Обнаружено в процессе дизайна:** этот разрыв прямо сейчас чинится в отдельном воркари `.claude/worktrees/office-hook-scratch-scan` (ветка `design-office-hook-scratch-bots`, `docs/OFFICE_HOOK_FROM_SCRATCH_BOTS.md`, uncommitted изменения в `runtime/registry.py`, `services/claude_service.py`). Решение: `append_from_scratch_registry_wiring()` детерминированно дописывает `config_from_bot_row`/`init_db`/`ConfigMiddleware`/(опц.) `on_office_event` в сгенерированный from-scratch файл, плюс `build_entry()` учится импортировать такой файл напрямую по `file_path` (не через `templates.<id>` namespace). После этого `module is not None` для from-scratch бота тоже, `typed_config` появляется, и **`_load_and_include_features()` начинает работать для них бесплатно** — никакого отдельного кода в notifications.py под это не нужно.

→ **notifications.py не должен решать эту часть сам.** Дождаться мержа той работы (или явно скоординироваться, чтобы не решать архитектуру дважды по-разному). Пока не влито — фича физически не подключится ни к одному from-scratch боту, только к template-based.

### 2.2 Разрыв в UI-предложении фичи (НЕ покрывается параллельной сессией — отдельная проблема)
Даже после 2.1, `handlers/manage_bots.py`'s `_compatible_features()`:
```python
return [f for f in discover_features() if template_id in f["compatible_with"]]
```
и `cb_toggle_feature()`'s guard `template_id not in feature["compatible_with"]` — оба используют `infer_template_id(file_path)`, которая для from-scratch бота (нет `# TEMPLATE:` маркера) возвращает `None`. `None in [список из ~30 template_id]` всегда `False` → кнопка "🧩 Фичи" никогда не предложит notifications (или payments/sheets/office_events) владельцу from-scratch бота, СКОЛЬКО БЫ template_id ни было в списке.

Это не специфично для notifications — тот же баг уже существует для payments/sheets/office_events сегодня, просто никто раньше не должен был явно называть from-scratch совместимым. Два пути закрыть:
- **(a) Явный сентинел** — `COMPATIBLE_WITH` получает магическое значение (например `*` или `__any__`) ТОЛЬКО когда автор фичи осознанно проектирует её template-agnostic (не трогает никакие таблицы, специфичные для конкретного шаблона). `_compatible_features()`/`cb_toggle_feature()` учатся: `template_id in compat OR "*" in compat`. Минимальное изменение, не трогает `discover_features()`'s "no all sentinel" инвариант для остальных 20+ фич (тот инвариант защищает от случайного расширения — здесь расширение осознанное и локальное к одной фиче).
- (b) Список всех template_id + отдельная ручная привязка от by-template к from-scratch — то, что владелец отверг в вопросе выше (придётся руками дописывать каждый новый шаблон/each generation).

**Рекомендация: (a).** Совпадает с тем, что notifications.py по своей природе НЕ зависит от структуры конкретного шаблона (в отличие от, скажем, sellable_items, которое трогает конкретные категории товаров) — она работает с "кто писал этому боту" (см. §3), что одинаково для любого бота. `*`/`__any__` — правка ~3 строк в `handlers/manage_bots.py`, не в `discover_features()`, и не открывает эту возможность остальным фичам автоматически.

**Это тоже отдельный кусок работы вне notifications.py самого — нужно подтверждение владельца, потом либо сделать здесь как часть этой задачи, либо отдельным PR.**

## 3. Аудитория рассылки: откуда брать список получателей

Инвентаризация показала: **нет общей таблицы "клиенты этого бота"**. Каждый шаблон хранит `user_id`/`chat_id` в своих собственных таблицах под своим именем колонки (`bookings.user_id`, `payments.user_id`, и т.д.) — нет единой конвенции, которую notifications.py могла бы просто прочитать по имени, тем более для from-scratch бота с произвольной схемой.

### Решение: собственная таблица подписчиков, populated пассивно
notifications.py заводит СВОЮ таблицу в host `db_path` (тот же паттерн, что payments.py — `init_notifications_tables(db_path)`), пример структуры (имена условные, финализируются при реализации):
```
subscribers (
    chat_id          INTEGER PRIMARY KEY,   -- пример: 123456789
    username         TEXT,                  -- пример: "ivan_petrov" или NULL
    subscribed_at    TEXT DEFAULT (datetime('now','localtime')),  -- "2026-08-16 10:15:00"
    unsubscribed_at  TEXT,                  -- NULL = подписан; иначе та же дата-строка
    UNIQUE(chat_id)
)
```
Пополняется НЕ ручным вводом, а автоматическим upsert на **любое** входящее сообщение от пользователя в личку боту — модуль экспортирует `router` с одним `message` observer с самым низким приоритетом (`router.message.register(_track_subscriber)`, без фильтра, только приватные чаты), который просто upsert'ит `chat_id`/`username` и НЕ гасит апдейт (`return` без `await message.answer(...)`, чтобы не мешать хендлерам хоста — тот же non-blocking принцип, что sheets.py's пустой router, только тут router не пустой, но пассивный).

Это работает одинаково для template-based и from-scratch бота — не зависит ни от чьей схемы, только от факта "юзер писал этому боту хотя бы раз". Не требует знания структуры `bookings`/`orders`/etc.

**Ограничение, которое нужно явно принять:** это НЕ "все, кто когда-либо взаимодействовал с ботом до включения фичи" — только те, кто напишет /начнёт диалог ПОСЛЕ того, как владелец включит notifications. Ретроактивного сбора из существующих таблиц шаблона нет (нет общей схемы, откуда брать). Если нужно retroactive — отдельная, per-template миграция, не тянет сюда без явного запроса.

### Фильтр по критерию — НЕ в MVP
Задача упоминает "фильтр по критерию, если есть подходящее поле" — инвентаризация не нашла ни одного поля, которое было бы у ЛЮБОГО бота одинаково (это уже специфика шаблона: "клиенты с активным абонементом" осмысленно только у booking_fitness). Разумный компромисс: MVP — только "все подписчики" / "все, кроме отписавшихся" (что и так одно и то же в схеме выше). Фильтрация — будущая фича поверх этой же таблицы, если у конкретного шаблона появится своя интеграция (не блокирует запуск).

## 4. Флоу рассылки (владелец → аудитория)

1. Владелец в боте нажимает кнопку "📢 Разослать сообщение" (владелец = `_is_owner`/`bot_admins`, тот же guard что payments/manage_bots — по аналогии с `moderator.py`'s admin-панелью, кнопки а не текстовые команды, см. `project_button_ui_design_rule`).
2. FSM: текст ИЛИ фото+подпись (одно сообщение, `Message.photo`/`Message.text`).
3. Подтверждение: показать черновик + счётчик получателей (`SELECT COUNT(*) FROM subscribers WHERE unsubscribed_at IS NULL`) + кнопки "Отправить" / "Отмена".
4. Рассылка — **фоновая задача** (не блокирует хендлер, `asyncio.create_task`), с прогресс-репортом владельцу по завершении ("разослано 142, ошибок 3, отписалось при рассылке 1" — Telegram отдаёт 403 Forbidden при блокировке бота юзером, это триггерит auto-unsubscribe, см. ниже).

## 5. Rate limiting — обязательно, иначе бан

Telegram Bot API: жёсткий лимит ~30 msg/sec суммарно на бота (сервер троттлит/банит превышающих), и отдельно ~1 msg/sec на ОДИН и тот же chat_id (bulk-notification рекомендация самого Telegram — избегать частой отправки в один чат, для приватных чатов помягче, но общий broadcast всё равно должен быть размазан).

Проектное решение: последовательная очередь с `asyncio.sleep` между отправками, целевой throughput ~25 msg/sec (запас от жёсткого потолка в 30) — не concurrent-с-семафором-на-скорость (проще рассуждать о порядке и легче поймать 429 с `retry_after`). При `TelegramRetryAfter` (aiogram кидает это исключение на 429) — respect `exception.retry_after`, не свой бэкофф. Один упавший `chat_id` (403/400) не должен прерывать всю рассылку — try/except на КАЖДУЮ отправку, тот же изоляционный принцип что `_load_and_include_features()`'s per-feature try/except.

Открытый вопрос владельцу: рассылка идёт **на одном общем event loop со всеми остальными ботами фабрики** (тот же класс проблемы, что Phase A payments' 10-секундного pre_checkout_query таймаута) — рассылка в 10 000 подписчиков при 25 msg/sec займёт ~7 минут, за это время другие боты на том же процессе продолжают отвечать нормально (throttle через sleep, не блокирующий wait), но стоит подтвердить ожидаемый масштаб аудитории, чтобы не спроектировать под сценарий, которого не будет.

## 6. Отписка — обязательна (антиспам-требование Telegram)

Каждое рассылочное сообщение получает inline-кнопку "🔕 Отписаться от рассылок" (`callback_data="notif_unsub"` — bot_id не нужен в данных колбэка, т.к. таблица подписчиков per-bot db, каждый бот и так изолирован своим db_path). Нажатие → `UPDATE subscribers SET unsubscribed_at = datetime('now','localtime') WHERE chat_id = ?`, подтверждение в чат. Плюс — как отмечено в §4 — 403 Forbidden при попытке отправить (юзер заблокировал бота) тоже трактуется как unsubscribe (нет смысла хранить мёртвый chat_id, следующая рассылка снова получит ту же ошибку впустую).

Отдельная команда/кнопка "🔔 Подписаться снова" не требуется как обязательная (юзер и так ресабскрайбится автоматически при следующем сообщении боту — `_track_subscriber` из §3 делает `unsubscribed_at = NULL` on any new message, не только на первый), но стоит явно показать текстом при отписке ("напишите боту снова, чтобы возобновить").

## 7. Итоговый список зависимостей и стопов

1. **Ждёт** мерж `design-office-hook-scratch-bots` (или эквивалентного решения) — без него `_load_and_include_features()` не подключит notifications ни одному from-scratch боту, только template-based.
2. **Требует отдельного, небольшого изменения** в `handlers/manage_bots.py` (`_compatible_features`/`cb_toggle_feature`) — сентинел в `COMPATIBLE_WITH` (`*`/`__any__`) для template-agnostic фич, иначе UI никогда не предложит фичу владельцу from-scratch бота, даже когда загрузка её уже поддерживает.
3. Аудитория строится ТОЛЬКО из тех, кто написал боту после включения фичи (пассивный upsert-router) — нет retroactive сбора из существующих таблиц шаблона.
4. Фильтр по критерию — вне MVP, нет общего поля across all templates.
5. Rate-limit — последовательная очередь ~25 msg/sec + respect `TelegramRetryAfter`, фоновая задача, per-send try/except.
6. Обязательная inline-кнопка отписки на каждом рассылочном сообщении + auto-unsubscribe на 403.
