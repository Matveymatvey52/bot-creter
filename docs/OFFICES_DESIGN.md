# "Офисы": обмен событиями между ботами одного владельца — инвентаризация и дизайн

Статус: ЧЕРНОВИК, СТОП перед реализацией. Ждёт решения владельца по разделу 6.

## 1. Текущая архитектура (факты из кода)

- **Один процесс, один реестр.** `runtime/combined_app.py` поднимает единственный
  aiohttp-процесс; `runtime/registry.py`'s `Registry` держит `dict[bot_id -> BotEntry]`
  в памяти этого процесса. Каждый входящий webhook `/webhook/{bot_id}` находит
  `BotEntry` по `bot_id` и диспетчеризует внутри уже живого процесса — **не
  отдельный процесс на бота** (в отличие от `services/bot_runner.py`'s subprocess-модели
  для polling-режима, который сейчас не основной прод-путь).
- **Изоляция — per bot_id, не per owner.** В `db/database.py` таблица `bots` не имеет
  колонки `owner_id`. Владелец всей фабрики — один Telegram ID из `.env` (`OWNER_ID`,
  see `handlers/create_bot.py:703,780`). Это **однопользовательская** система: сейчас
  нет модели "несколько владельцев, у каждого свой пул ботов" — есть один владелец
  и один пул ботов, которые он создал через фабрику.
  → Это меняет постановку задачи: "офисы между ботами ОДНОГО владельца" в текущей
    архитектуре означает "офисы между ЛЮБЫМИ двумя ботами в реестре", потому что
    других владельцев не существует. Если это неверно и множественность владельцев
    планируется — см. открытый вопрос в разделе 6.
- **Данные изолированы по файлу БД.** Каждый tenant-бот получает собственный
  SQLite-файл `DATA_DIR/bot_{bot_id}_data.db` (`templates/tour_operator.py:180` и
  аналогично в других шаблонах — `config_from_bot_row()` по конвенции). Никакого
  общего DB-соединения между ботами нет: `_build_generic_middleware()` вызывает
  `module.init_db(config.db_path)` для каждого бота отдельно.
- **Роутеры полностью изолированы по конструкции.** `_clone_router()` в
  `registry.py:218` явно существует потому, что aiogram запрещает один `Router`
  на нескольких `Dispatcher`. Каждый бот получает свой клон роутера — обработчики
  общие по коду (stateless callbacks), но их состояние (FSM storage — `MemoryStorage()`
  на каждый `Dispatcher`, `registry.py:606`) не пересекается.
- **bot_id инжектируется в data**, но только внутрь ОДНОГО бота: `_attach_bot_id_middleware()`
  (registry.py:304) явно документирует, что bot_id одного бота никогда не должен
  утечь в хендлеры другого — это существующий инвариант, который "офисы" обязаны
  сохранить.
- **Единственный кросс-бот механизм сейчас** — group-scoped уведомления в
  `handlers/moderator.py` (DM-first с fallback в группу), но это про уведомление
  ЛЮДЕЙ в чатах, не бот→бот обмен данными.

Вывод: сейчас нет никакого существующего механизма, которым один бот мог бы
вызвать код или прочитать данные другого бота. Полностью новая подсистема.

## 2. Сценарии первого применения — 3 варианта

### Вариант A: событие → уведомление (fire-and-forget)
`tour_operator` создал заказ → `cashflow_ledger`-бот получает уведомление и
записывает приход в свою бухгалтерию.

- Плюсы: минимальная связность — bot B ничего не знает о внутренней логике bot A,
  кроме контракта события. Не блокирует обработку webhook'а bot A (можно сделать
  fire-and-forget, `asyncio.create_task`). Похоже на уже существующий паттерн
  `_load_and_include_features()` — независимая, изолированная по try/except обработка.
- Минусы: at-least-once/at-most-once не гарантируется без очереди — если процесс
  упадёт между "заказ создан" и "событие доставлено", событие теряется молча
  (no persistence, no retry). Для бухгалтерии это может быть неприемлемо (пропущенный
  приход = расхождение в кассе).

### Вариант B: событие → синхронный внутренний вызов (RPC-подобный)
Клиент написал сообщение в `support_bot` → внутри того же процесса напрямую
вызывается функция `crm_bot`'а, которая создаёт тикет, и результат (например,
номер тикета) возвращается обратно для ответа клиенту.

- Плюсы: результат сразу доступен вызывающему боту — можно, например, ответить
  клиенту "Ваш тикет #42 создан" в том же сообщении. Раз всё в одном процессе
  (`combined_app.py`), синхронный вызов — это просто `await` другой функции, без
  сети/сериализации.
- Минусы: связность становится куда теснее — bot A явно знает сигнатуру функции
  bot B. Ошибка в bot B (исключение, зависший `await`) теперь блокирует обработку
  webhook'а bot A, если не обёрнута аккуратно — а `_load_and_include_features()`'s
  докстринг уже описывает похожий риск (`answerPreCheckoutQuery`'s 10s окно) для
  куда более лёгких операций типа импорта модуля. RPC между ботами — тяжелее и
  рискованнее в этом смысле.

### Вариант C: событие → шина внутри процесса с подписками (pub/sub)
Общий `EventBus` в `combined_app.py`: любой бот публикует событие типа
`("order.created", bot_id=A, payload={...})`; любой другой бот, подписавшийся на
`order.created` от bot_id=A (через новую таблицу связей), получает его асинхронно.

- Плюсы: расширяемо на N:M отношения без переписывания кода при добавлении
  третьего/четвёртого связанного бота. Явная точка конфигурации (таблица связей) —
  владелец видит и управляет, кто на что подписан, через UI фабрики (в духе
  `handlers/custom_features.py`'s "✅ Применить"-паттерна).
- Минусы: больше всего нового кода и поверхности для багов из всех трёх вариантов.
  Требует продумать доставку (at startup vs runtime), retry, порядок событий,
  что если подписчик офлайн/бот удалён посреди обработки.

### Рекомендация
Начать с **варианта A** (fire-and-forget уведомление, in-memory, без персистентности
в первой итерации) как MVP — он ближе всего к существующим паттернам
(`_load_and_include_features()`'s per-item try/except isolation), не блокирует
критический путь webhook'а, и достаточен для сценария "заказ → уведомление в
бухгалтерию". Вариант C (полноценная шина с таблицей подписок) — естественное
развитие A, если понадобится больше одной пары ботов или условная маршрутизация.
Вариант B (синхронный RPC) — только если появится конкретный сценарий, где
результат нужен СРАЗУ в рамках одного ответа пользователю; иначе не заводить.

## 3. Набросок механизма (для обсуждения, не для реализации)

Если выбирается направление A/C:

- **Таблица связей** (аналог `bot_features`): `bot_office_links(source_bot_id,
  target_bot_id, event_type, created_at)` — кто на что подписан. `PRIMARY KEY
  (source_bot_id, target_bot_id, event_type)`, оба FK на `bots(id)`.
- **Публикация**: библиотечная функция (`features/office_events.py`?) с сигнатурой
  вроде `await publish_event(bot_id: int, event_type: str, payload: dict)`,
  вызываемая ИЗ шаблона (как `features/payments.py::create_invoice()` сейчас
  вызывается из `tour_operator.py`) — не хендлер, а библиотека.
- **Доставка**: `publish_event()` смотрит `bot_office_links` на bot_id-источник,
  для каждого подписанного `target_bot_id` находит `BotEntry` в живом `Registry`
  (тот же `registry.get(target_bot_id)`, что уже использует webhook-путь) и
  вызывает целевой обработчик — по аналогии с `_load_and_include_features()`'s
  try/except-per-item, ОДИН упавший подписчик не должен ронять публикацию для
  остальных.
- **Хранение состояния подписки** — в главной `bots.db` (`db/database.py`), не в
  per-bot файлах: связи между ботами — это метаданные владельца о своих ботах,
  а не данные конкретного бота.

Это направление, не спецификация — нужно решение владельца сначала (раздел 6).

## 4. Риски изоляции данных

- **Данные ДРУГИХ владельцев.** Сейчас архитектура однопользовательская (раздел 1),
  так что риска "офис между чужими ботами" физически нет — подписка возможна
  только между bot_id, оба из которых существуют в одном `bots`-реестре одного
  `OWNER_ID`. Но если система когда-либо станет мультитенантной (несколько
  факторий/владельцев на одной инсталляции), таблица `bot_office_links` ОБЯЗАНА
  проверять, что `source_bot_id` и `target_bot_id` принадлежат одному владельцу —
  иначе бот владельца X сможет подписаться на события бота владельца Y. Прямо
  сейчас в схеме `bots` нет `owner_id` вообще, так что этот риск сейчас не
  проверяем в принципе — если офисы задизайнены без owner_id-проверки, а
  multi-owner добавят позже, это станет дырой безопасности задним числом.
- **Полезная нагрузка события — это утечка данных другого бота внутрь.** Если
  `payload` в `publish_event()` содержит сырые записи из БД bot A (например,
  персональные данные клиента), а bot B сохраняет их в СВОЮ БД — это осознанное
  копирование данных между изолированными хранилищами. Нужно явно решить: событие
  несёт МИНИМАЛЬНО необходимые поля (id заказа, сумма) или произвольный payload
  на усмотрение шаблона. Рекомендация: типизированный, явно ограниченный контракт
  события на event_type, а не "прокинь что хочешь" — иначе легко случайно
  протащить лишнее (телефон клиента и т.п.) туда, где оно не нужно и не ожидалось.
- **bot_id-инъекция остаётся строгой внутри целевого бота.** `_attach_bot_id_middleware()`'s
  инвариант (bot_id одного бота не течёт в хендлеры другого) должен сохраниться:
  обработчик входящего офисного события в bot B получает `bot_id=B` как обычно,
  а `source_bot_id=A` — как отдельное явное поле payload'а, не подмена контекста.
- **Reload/удаление бота.** `Registry.reload_one()`/`remove()` уже могут убрать бота
  из реестра в рантайме. Если bot A подписан на bot B, а B удалён — `bot_office_links`
  станет содержать dangling FK. Нужна либо `ON DELETE CASCADE`, либо явная чистка
  в хендлере удаления бота (`handlers/manage_bots.py`), аналогично тому, как уже
  обрабатывается `bot_features`/`bot_custom_features` при удалении (не проверено в
  рамках этой инвентаризации — стоит проверить перед реализацией).

## 5. Итог инвентаризации

Нет существующего кросс-бот механизма — начинать с нуля. Архитектура
однопроцессная (`combined_app.py` + `Registry`), что делает синхронный/асинхронный
in-memory обмен дешёвым технически (нет сети, нет сериализации между ботами) —
но систему владелец задизайнил и держит строго per-bot-изолированной по данным
(отдельный SQLite-файл на бота, `_attach_bot_id_middleware`'s явный инвариант),
так что "офисы" — это первый осознанный пролом в этой изоляции, и он должен быть
узким и explicit (таблица связей + типизированный контракт событий), а не общей
шиной, куда любой бот может слушать что угодно.

## 6. Открытые вопросы для владельца — СТОП здесь

1. **Multi-owner в планах?** Если да — `bots.owner_id` нужно добавить ДО офисов
   (иначе "офисы" придётся передизайнивать под owner-scoping задним числом).
   Если нет — можно спокойно считать "все боты в реестре — один офис-пул".
2. **Какой из вариантов A/B/C первый?** Рекомендация — A (fire-and-forget
   уведомление), но нужен конкретный первый use-case от владельца, чтобы не
   гадать на пустом сценарии.
3. **Нужна ли персистентность события** (переживает рестарт процесса) или
   in-memory fire-and-forget приемлем для первой итерации? Railway передеплой
   перезапускает процесс — недоставленные события пропадут при варианте
   "без персистентности".
4. **Контракт payload'а** — фиксированный список типов событий с явной схемой
   полей, или произвольный dict на усмотрение шаблона?
