# Дизайн: userbot-инфраструктура для `channel_monitor` (Telegram Client API)

Продолжение [docs/CHANNEL_MONITOR_DESIGN.md](CHANNEL_MONITOR_DESIGN.md) — тот документ описывал
урезанный Bot-API-вариант ("только каналы, куда бот добавлен админом"), который был отклонён
владельцем в пользу полноценного мониторинга произвольных чужих каналов. Это принципиально другая
инфраструктура: не бот, а **клиентский аккаунт** (userbot) через Telethon.

**Это дизайн-документ. Кода нет. Стоп в конце — обязательно дождаться подтверждения.**

---

## 0. Что уже есть в фабрике (проверено по коду)

- Один Railway-сервис, один процесс: `runtime/combined_app.py` — вебхук aiohttp-сервер,
  все боты фабрики (арендаторы + сама фабрика под `FACTORY_BOT_ID`) отвечают через один и тот же
  `/webhook/{bot_id}` в одном event loop ([runtime/combined_app.py](../runtime/combined_app.py)).
  `main.py` (long-polling) — только для локальной разработки, в проде не используется.
- Шифрование токенов ботов: `db/database.py` — `Fernet(ENCRYPTION_KEY)`, `_encrypt_token`/
  `_decrypt_token`, с миграцией с plaintext (`migrate_encrypt_tokens`), детектом "не удалось
  расшифровать = либо не мигрировано, либо ключ сменился" ([db/database.py:7-82](../db/database.py)).
  Один `ENCRYPTION_KEY` на всю фабрику, из окружения (Railway Variables).
- Деплой: `railway.toml` → `bash start.sh` → `exec python ${BOT_SCRIPT:-main.py}`, `BOT_SCRIPT`
  указывает на `runtime/combined_app.py` в проде.

## 1. Хранение сессии Client API

Сессия Telethon (`StringSession`) — по значимости эквивалентна паролю от аккаунта клиента:
обладатель строки может полностью управлять аккаунтом без пароля и без кода. Схема:

- **Формат**: `StringSession` (не файл `.session` на диске) — Telethon умеет сериализовать сессию
  в строку, что удобнее для БД (одна колонка) и для деплоя (нет файлов сессий, разбросанных по
  диску контейнера, которые исчезнут при рестарте Railway — эфемерная файловая система).
- **Шифрование**: тот же паттерн, что уже есть для токенов ботов — `Fernet(ENCRYPTION_KEY)`.
  **НЕ переиспользовать сам `ENCRYPTION_KEY`** для нового типа секрета без явного решения владельца:
  предлагается отдельная переменная окружения `USERBOT_ENCRYPTION_KEY`, чтобы ротация одного ключа
  (например, при подозрении на утечку токенов ботов) не требовала одновременной ротации доступа
  к userbot-сессиям, и наоборот. Тот же `_encrypt_token`/`_decrypt_token`-паттерн (функции,
  не хардкод) переносится один в один на новую таблицу.
- **Таблица** (в центральной БД фабрики, не в БД конкретного бота — сессия принадлежит клиенту
  фабрики, а не конкретному "боту-продукту"):

```sql
CREATE TABLE userbot_sessions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_user_id INTEGER NOT NULL,       -- Telegram id владельца (клиента фабрики)
    phone TEXT NOT NULL,                  -- на который заведён userbot, для отображения/повторной авторизации
    session_string TEXT,                  -- Fernet-encrypted StringSession; NULL пока авторизация не завершена
    status TEXT DEFAULT 'pending',        -- pending | active | revoked | auth_failed
    created_at TEXT DEFAULT (datetime('now','localtime')),
    updated_at TEXT DEFAULT (datetime('now','localtime'))
);
```

- **Доступ**: расшифрованная сессия существует только в памяти процесса userbot-воркера на время
  подключения — никогда не логируется, не уходит в Gemini, не появляется в текстах, отправляемых
  владельцу.
- **Отзыв**: у владельца в боте фабрики — кнопка «🔴 Отключить мониторинг» → `status='revoked'`,
  процесс получает сигнал остановить клиент Telethon и обнулить сессию в памяти. Строка в БД
  не удаляется сразу (оставляем `revoked` для аудита), но `session_string` затирается (`NULL`)
  — восстановить соединение после отзыва можно только повторной полной авторизацией.

## 2. FSM первичной авторизации (диалог с ботом фабрики)

Состояния (aiogram FSM, отдельная `StatesGroup`, например `UserbotAuthStates`):

1. **`waiting_phone`** — бот просит номер телефона в международном формате.
   Технически: `TelegramClient(StringSession(), api_id, api_hash)` создаётся, `client.connect()`,
   затем `client.send_code_request(phone)` → возвращает `phone_code_hash`, который нужно сохранить
   (в FSM-контексте, не в БД — это промежуточные данные одной авторизационной попытки) для
   следующего шага.
2. **`waiting_code`** — бот просит код, который Telegram прислал клиенту **в его же аккаунт**
   (не через SMS обязательно — обычно как сообщение от Telegram в самом приложении). Клиент вводит
   код текстом в бота фабрики. Технически: `client.sign_in(phone, code, phone_code_hash=...)`.
   - Ошибка `PhoneCodeInvalidError` → остаться в `waiting_code`, попросить ввести код заново
     (со счётчиком попыток, чтобы не долбить Telegram).
   - Ошибка `PhoneCodeExpiredError` → код устарел, вернуться в `waiting_phone`, запросить новый.
3. **`waiting_2fa_password`** (условный, только если возникает) — если у клиента включена 2FA,
   `sign_in` бросает `SessionPasswordNeededError`. Бот просит пароль облачного пароля (не Telegram-
   пароль от кода, а именно 2FA cloud password). Технически: `client.sign_in(password=...)`.
   - Ошибка `PasswordHashInvalidError` → остаться в этом состоянии, попросить пароль заново.
4. **Успех** — `client.session.save()` → строка сессии → шифруется → пишется в `userbot_sessions`
   (`status='active'`). Диалог завершается сообщением с явным перечислением рисков (см. §6) —
   не просто "готово", а подтверждение, что клиент их видел, при первом запуске.

Общие ошибки на любом шаге:
- **`FloodWaitError`** — Telegram просит подождать N секунд перед следующей попыткой. Бот сообщает
  клиенту точное время ожидания и НЕ делает автоматический retry раньше этого срока (это тот самый
  паттерн поведения, что триггерит подозрение на автоматизацию/бан — игнорировать `FloodWaitError`
  нельзя ни при каких обстоятельствах).
- **`PhoneNumberInvalidError`** — некорректный формат номера, остаться в `waiting_phone`.
- Любой незнакомый exception на этапе `sign_in` → лог + понятное сообщение клиенту («не удалось
  войти, попробуйте позже») + сброс FSM в начало, не оставлять "полуавторизованный" клиент висеть
  в памяти.

## 3. Процессная модель и деплой

**Не в `combined_app.py`.** Обоснование: aiogram-боты в combined_app обрабатывают события
per-request через один общий aiohttp event loop без долгоживущих фоновых подключений — это
принципиально webhook-модель (Telegram сам стучится к нам). Telethon-клиент — наоборот, обязан
держать **собственное постоянное соединение** (MTProto) к серверам Telegram, которое живёт
независимо от входящих HTTP-запросов. Смешивать их в одном процессе технически возможно
(общий event loop), но операционно рискованно: падение/тормоз одного userbot-соединения не должен
уронить обработку вебхуков всех арендованных ботов фабрики — а в одном процессе гарантий изоляции
между корутинами нет (одна зависшая корутина может застопорить весь loop).

**Предложение**: отдельный **новый Railway-сервис** в том же проекте — `userbot-worker` (или
аналогичное имя), отдельный `BOT_SCRIPT`/entry point (`runtime/userbot_worker.py`), со своим
собственным процессом и event loop, читающий ту же центральную БД фабрики (`userbot_sessions` +
таблицы мониторинга, см. §4) через тот же файл БД/тот же connection-паттерн, что и combined_app,
если БД остаётся SQLite на общем volume, либо через сетевое подключение, если к тому моменту БД
уже вынесена в отдельный сервис — но это отдельный вопрос, не блокирующий этот дизайн.

**Внутри одного `userbot-worker`-процесса — мультиплексирование, не процесс на клиента.**
Один `TelegramClient` = одна asyncio-задача (`client.run_until_disconnected()` в фоне через
`asyncio.create_task`), несколько клиентов = несколько задач в одном event loop одного процесса.
Обоснование: процесс на каждого userbot-клиента фабрики плохо масштабируется операционно (Railway
per-service overhead, отдельный мониторинг каждого) при вероятно небольшом количестве одновременных
клиентов на старте продукта; мультиплексирование в одном asyncio-процессе — стандартный паттерн
для Telethon (используется в open-source юзербот-фреймворках). Если число активных userbot-клиентов
вырастет настолько, что один процесс станет узким местом — это отдельная задача горизонтального
шардирования (несколько `userbot-worker` реплик, каждая обслуживает подмножество `owner_user_id`
по консистентному хэшу), не требующая пересмотра этого дизайна, только добавление шардинг-слоя.

**Restart/recovery**: при рестарте `userbot-worker` (деплой, краш) — на старте читает все строки
`userbot_sessions` со `status='active'`, расшифровывает сессии, поднимает `TelegramClient` для
каждой заново (тот же паттерн, что `restore_bots()` в `main.py` делает для арендованных ботов).

## 4. Схема данных собранного контента

Переиспользуем `monitored_channels`/`channel_posts` из раннего дизайна с изменениями: убираем
привязку "канал только если бот там админ", добавляем привязку к владельцу (один userbot-клиент
может мониторить много каналов, и разные клиенты фабрики не должны видеть чужие списки):

```sql
CREATE TABLE monitored_channels (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    owner_user_id INTEGER NOT NULL,        -- чей это userbot / чья лента
    channel_username TEXT,                 -- @username, как ввёл клиент
    channel_id INTEGER,                    -- заполняется после resolve через client.get_entity()
    channel_title TEXT,
    active INTEGER DEFAULT 1,
    added_at TEXT DEFAULT (datetime('now','localtime'))
);

CREATE TABLE channel_posts (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    monitored_channel_id INTEGER NOT NULL, -- FK -> monitored_channels.id
    message_id INTEGER,
    text TEXT,
    posted_at TEXT DEFAULT (datetime('now','localtime')),
    summary TEXT                            -- заполняется Gemini-суммаризацией, см. §5
);
```

**Подписка на канал**: клиент вводит `@username` или ссылку в боте фабрики → userbot-worker
резолвит его через `client.get_entity(username)` и, если канал публичный, **вступает**
(`client(JoinChannelRequest(entity))`) — Client API это разрешает для публичных каналов без
приглашения администратора. Если канал приватный (по инвайт-ссылке `t.me/+...` или закрытый) —
`get_entity`/`JoinChannelRequest` завершится ошибкой доступа; в этом случае бот сообщает клиенту
явно: «Этот канал закрытый — мониторинг возможен только если ваш аккаунт уже состоит в нём или
получит приглашение отдельно» (частный случай, не путать с "молчаливым провалом" — тот же принцип
явного объяснения, что был в старом дизайне для Bot-API-ограничения).

**Сбор постов**: как только userbot вступил в канал, Telethon-клиент подписан на новые события
через `client.on(events.NewMessage(chats=channel_id))` — принципиально то же, что `channel_post`
у Bot API, но доступно для любого канала, куда вступил именно userbot, а не только там, где он
администратор. История ДО вступления недоступна и через Client API тем же образом (Telegram не
отдаёт историю канала, актуальную "до того как ты туда зашёл", для рядовых участников —
только для админов канала, что для чужих каналов недостижимо в любом случае).

## 5. Точка интеграции Gemini

Разделение чёткое: Gemini получает **только текст постов** (`channel_posts.text`), никогда —
`session_string`, номер телефона, `api_id`/`api_hash`, или что-либо, идентифицирующее аккаунт
клиента сверх самого текста контента.

- Отдельный сервис `services/gemini_service.py` (по аналогии с существующим
  `services/claude_service.py`, но не переиспользующий его — другой провайдер, другой ключ,
  `GEMINI_API_KEY` отдельной переменной окружения).
- Точка вызова: фоновая задача в `userbot-worker` (не блокирующая приём новых постов) — на каждый
  новый пост или пачкой (например, раз в N минут суммаризирует накопившиеся необработанные посты
  активных каналов) вызывает Gemini с промптом "кратко суммируй" → пишет результат в
  `channel_posts.summary`.
- «📰 Лента» в боте фабрики показывает `summary`, если есть, иначе — обрезанный `text` (Gemini-
  вызов может быть асинхронным/с задержкой, лента не должна ждать его синхронно).
- Ошибка Gemini API (таймаут, квота) → `summary` остаётся `NULL`, лента показывает сырой текст,
  ретрай — не блокирующий пайплайн (та же философия деградации, что в остальной фабрике: провал
  необязательного обогащения не должен ронять основной поток данных).

## 6. Риски — текст в самом боте при онбординге (не только в этом документе)

Перед завершением FSM-авторизации (§2, шаг 4) и до первого запроса номера телефона — экран с
явным текстом, требующим подтверждения нажатием кнопки «Понимаю и продолжаю» перед тем, как
бот примет номер телефона:

> ⚠️ Мониторинг чужих каналов работает через ваш **личный Telegram-аккаунт**, а не через бота.
> Это значит:
> - Telegram может ограничить или заблокировать этот аккаунт, если сочтёт его поведение
>   автоматизированным (массовое вступление в каналы, частые запросы) — такой риск реален и
>   неустраним полностью на нашей стороне.
> - Массовый сбор контента из чужих каналов может нарушать условия использования Telegram —
>   ответственность за то, какие каналы вы мониторите и как используете собранные данные, лежит
>   на вас.
> - Мы технически предоставляем инструмент для авторизации и мониторинга, но не гарантируем
>   сохранность вашего аккаунта и не несём ответственности за его блокировку.
>
> Продолжая, вы подтверждаете, что понимаете эти риски.

Это же — сжато — на кнопке «➕ Подключить мониторинг» до входа в сам FSM, чтобы клиент видел риск
раньше, чем начнёт вводить номер телефона.

## 7. Стоп

Этот документ закрывает архитектурные вопросы, поставленные в ТЗ: хранение сессии (Fernet,
отдельный `USERBOT_ENCRYPTION_KEY`), FSM авторизации через Telethon с обработкой характерных
ошибок, процессная модель (отдельный Railway-сервис `userbot-worker`, мультиплексирование клиентов
в одном процессе, не процесс на клиента), схема данных мониторинга привязанная к владельцу, точка
интеграции Gemini (только текст постов, отдельный ключ), и текст рисков для онбординга в самом
боте.

Кода нет — это дизайн-этап. Жду подтверждения от владельца перед реализацией.
