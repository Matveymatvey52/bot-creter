## 1. Что есть сейчас (инвентаризация)

**Логирование** (`db/database.py`, влито):
- `template_candidates` — одна строка на бота, упавшего в from-scratch. Поля: `summary` (сырой текст
  требований), `fallback_reason` (`no_template_match` / `customize_failed` / `hybrid_failed` /
  `synthesis_failed`), `selected_templates` (JSON, может быть пуст), `bot_type`, `bot_id`, `creator_user_id`,
  `bot_name`, `created_at`.
- Пишется из `handlers/create_bot.py:771` (`_finalize_bot_creation`), сразу после
  `create_bot_record_with_admins`, если `fallback_info` не `None`.
- `bot_type` считается `classify_bot_type()` (`services/claude_service.py:824`) — Haiku-классификатор
  в **фиксированный словарь из 5 значений**: `booking | manager | moderator | table | general`
  (`_BOT_TYPE_EXTRAS`, :815). Это слишком грубо для целей этой задачи: два никак не связанных
  from-scratch запроса ("голосовой учёт денег для шиномонтажа" и "модерация чата с банхаммером")
  вполне могут оба попасть в `general`, а два *похожих* запроса ("голосовой cashflow для шиномонтажа"
  vs "голосовой cashflow для доставки") — в разные корзины, если один зацепил `booking` по случайному
  слову. `bot_type` был задуман для другой цели (подбор `_BOT_TYPE_EXTRAS` промпта при генерации),
  переиспользовать его как кластеризационный ключ для этой задачи не стоит.
- **Никакого эмбеддинга/векторного представления `summary` сегодня не считается и не хранится.**

**Отображение** (`/analytics` — REST + React miniapp):
- `runtime/factory_analytics_api.py:104` `list_template_candidates_handler` → `GET /api/factory/candidates`,
  owner-only через `_authenticate_owner()`, отдаёт `list_template_candidates()` как есть (raw rows,
  без группировки на сервере).
- `miniapp/src/screens/FactoryDashboardScreen.tsx:70` `TemplateCandidatesSection` — единственная
  группировка сегодня: **клиентская**, `Map` по `bot_type`, отсортирована по размеру группы.
  Комментарий в коде сам называет это "Lightweight signal, not real clustering".
- Общий раздел `/analytics` также считает шаблон/время/токены на бота (`list_bots_with_stats`),
  но это про уже классифицированные (template_id не null) боты — не про эту задачу.

Вывод: **инфраструктура сбора полностью готова и в master**; не хватает только слоя между "сырые
строки в БД" и "секция дашборда" — собственно кластеризации.

## 2. Что кластеризовать и почему LLM, а не эмбеддинги

Вход кластеризации — поле `summary` (`requirements_summary`, готовое резюме диалога сбора требований,
не сырой голос/текст пользователя целиком — оно уже синтезировано `chat_gather_requirements` в
`handle_gathering`). Это удобно: `summary` уже на русском, компактное, семантически насыщенное — не
нужно отдельно нормализовать голосовой ввод.

Два кандидата на метод группировки:

**(a) Эмбеддинги + косинусная близость / HDBSCAN.**
Плюсы: дёшево на инференсе (эмбеддинг считается один раз при вставке строки, кластеризация — чистая
линейная алгебра, без доп. LLM-вызовов на каждый пересчёт). Минусы: в проекте сегодня нет ни одной
интеграции с embeddings API (Anthropic API эмбеддингов не отдаёт — нужен сторонний провайдер, напр.
Voyage AI, либо OpenAI), это новая зависимость и новый секрет в `.env`. Плюс подбор порога similarity
и алгоритма кластеризации (HDBSCAN тянет `scikit-learn`/`hdbscan` как зависимость) требует эмпирической
настройки, которую сложно провалидировать при нынешнем объёме кандидатов (пока их считаные десятки).

**(b) LLM-классификация в динамический список доменов (без ML-стека).**
Один вызов Haiku, которому на вход даётся весь пока не кластеризованный batch `summary` (или новые
строки + уже существующий список доменных меток из прошлого прогона), и который либо относит каждую
строку к уже существующей метке, либо заводит новую. Держит проект в русле уже принятого паттерна
(весь classify-слой — Haiku-вызовы: `_select_template`, `classify_bot_type`,
`CONNECT_FEATURE_CLASSIFY_PROMPT` и т.д. — ни разу не заводили embeddings/векторную БД). Минус —
стоимость растёт с числом кандидатов, если пересчитывать с нуля каждый раз; решается инкрементальным
подходом (§3).

**Рекомендация: (b), LLM-классификация**, по тем же причинам, что и выбор (b) в предыдущем дизайне —
согласованность с существующим стилем кода, отсутствие новой инфраструктурной зависимости, объём
данных (десятки-сотни строк, не тысячи) не оправдывает векторный поиск. Если объём вырастет на
порядки, эмбеддинги стоит пересмотреть — но не сейчас.

## 3. Механизм: периодический batch-джоб, инкрементальный

### Хранение кластеров
Новая таблица `template_candidate_clusters` в `db/database.py::init_db()`, тем же паттерном:

```sql
CREATE TABLE IF NOT EXISTS template_candidate_clusters (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    label         TEXT NOT NULL,        -- короткая метка домена от LLM, напр. "voice-учёт расходов для сервисов"
    description   TEXT,                 -- 1-2 предложения, что объединяет кластер (для владельца)
    created_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at    TIMESTAMP DEFAULT CURRENT_TIMESTAMP
)
```

Связь кандидат→кластер строго 1:1 (не multi-label) — **рекомендация: добавить nullable колонку
`cluster_id INTEGER REFERENCES template_candidate_clusters(id)` прямо в `template_candidates`**,
а не отдельную join-таблицу (JOIN не нужен при 1:1). Это первая колонка, добавляемая в уже
существующую таблицу этим механизмом — `CREATE TABLE IF NOT EXISTS` её не создаст на старых базах,
нужен явный `ALTER TABLE template_candidates ADD COLUMN cluster_id INTEGER REFERENCES
template_candidate_clusters(id)`, обёрнутый проверкой "если колонки ещё нет" (через
`PRAGMA table_info` или try/except на `duplicate column` — по образцу существующих миграций-добавлений
колонок в `db/database.py`, если такой прецедент там уже есть — свериться перед реализацией).

### Периодичность и триггер
Не realtime (кластеризация после каждой new-row вставки — избыточные LLM-вызовы на единичных
событиях, тем более что смысл появляется только при накоплении повторов). Варианты:
- **По расписанию** (напр. раз в сутки, фоновый джоб) — пересчитывает кластеры для всех
  `cluster_id IS NULL` строк.
- **Лениво при открытии `/analytics`** — сложнее: dashboard-запрос не должен блокироваться на
  LLM-вызове, плюс authenticated-only endpoint дергается многократно, нет естественной идемпотентности
  "уже посчитано сегодня" без доп. состояния.

**Рекомендация: по расписанию**, простой батч-джоб (не веб-хендлер) с флагом "запускать раз в N часов"
— конкретный механизм (APScheduler vs cron vs ручной пересчёт для владельца) зависит от того, что уже
используется в проекте для фоновых задач — нужно свериться с существующим кодом `runtime/`, прежде чем
предлагать новую зависимость.

### Алгоритм инкрементального прохода
1. Выбрать все `template_candidates` с `cluster_id IS NULL` (новые с прошлого прогона).
2. Собрать текущий список существующих кластеров (`label` + `description`) как контекст.
3. Один (или несколько батчами, если новых строк много) Haiku-вызов: "вот список уже известных доменов
   с описаниями, вот N новых запросов (summary + bot_type) — для каждого либо верни id существующего
   домена, которому он соответствует, либо предложи новую метку домена". Промпт — по образцу
   существующих classify-промптов (`CONNECT_FEATURE_CLASSIFY_PROMPT` как референс структуры).
4. Записать `cluster_id` на каждую строку; для новых меток — вставить строку в
   `template_candidate_clusters`, затем проставить её id.
5. Не трогать уже кластеризованные строки задним числом (никакого re-clustering всего датасета каждый
   раз) — это держит стоимость линейной от новых кандидатов, а не квадратичной от общего объёма, и не
   "плавает" метка кластера под ногами владельца между просмотрами.

Важный компромисс, который стоит явно принять: инкрементальный подход может со временем породить
дублирующиеся близкие кластеры (LLM не увидела связи между "учёт расходов голосом" и "голосовой ввод
трат" в разных батчах). Смягчение — держать `description` кластера содержательным и передавать *весь*
существующий список меток (не только "похожие") в промпт на каждом проходе, чтобы модель имела шанс
смержить. Полного решения без периодического ручного review владельцем (или редкого полного
re-cluster) не предлагается — и не обязательно: конечный шаг всё равно ручной (владелец решает, что
стало отдельным шаблоном), небольшое дублирование кластеров не критично, если счётчики всё равно
видны.

## 4. Отображение в /analytics

Новая секция **"Топ незакрытых паттернов"** (вместо/рядом с нынешней группировкой по `bot_type` в
`TemplateCandidatesSection`):

- Новый эндпоинт `GET /api/factory/candidate-clusters` в `runtime/factory_analytics_api.py`, тот же
  `_authenticate_owner()`. Отдаёт кластеры, отсортированные по размеру (кол-во кандидатов), с полями
  `label`, `description`, `count`, `first_seen`/`last_seen` (min/max `created_at` среди участников),
  и списком примеров `summary` (напр. первые 3) — чтобы владелец читал реальный текст запроса, не
  только сгенерированную метку (тот же принцип "raw text, не эвристика", что был в исходном дизайне
  §3 для сырых строк).
- Некластеризованные записи (`cluster_id IS NULL`, ещё не подхвачены батч-джобом) — показывать отдельным
  блоком "Ещё не обработано" или просто исключать до следующего прогона; не блокировать интерфейс их
  ожиданием.
- Явный сигнальный порог в UI (не в БД) — напр. подсветка кластеров с `count >= 3` как "стоит
  рассмотреть шаблон" — чистое отображение, порог не жёсткий бизнес-инвариант, можно менять в коде
  фронтенда без миграций.
- Старую группировку по `bot_type` можно оставить как вторичный фильтр/сортировку внутри секции (она
  дёшева, уже есть), либо убрать, если новая секция её полностью покрывает — решение не критично,
  можно оставить на усмотрение реализации.

Финальное решение "оформить кластер в постоянный `templates/*.py`" остаётся полностью ручным — как и
в исходном дизайне: автоматической генерации шаблона из кластера не предлагается.
