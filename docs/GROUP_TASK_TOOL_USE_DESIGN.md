# Групповой ТЗ-канал: tool-use режим (владелец реально выполняет действия)

Статус: РЕАЛИЗОВАНО, ветка `group-task-tool-use`. Продолжение
`docs/GROUP_TASK_CHANNEL_DESIGN.md` §6-7, вопрос №1 которого владелец
подтвердил: v1 канала был "чат, не агент"; эта задача добавляет
tool-use поверх того же `features/group_task.py`.

## 0. Инвентаризация — что уже было готово

- `features/group_task.py` — chat-режим на Haiku, без доступа к БД бота.
- Единственный реально ПЕРЕИСПОЛЬЗУЕМЫЙ CRUD-слой (одинаковый в любом
  боте, где включён) — feature-модули: `features/sellable_items.py`
  (`_create_item`/`_update_item_field`/`_toggle_item_active`) и
  `features/payments.py` (`record_refund`).
- У шаблонов (`templates/*.py`) НЕТ общей схемы — `tour_operator.py`
  хранит tours/program/locations/hotels/guests, `shop_catalog.py` —
  свои таблицы и т.д., каждый ad-hoc. Единый generic tool на все 27
  шаблонов потребовал бы либо per-template tool-схем (27x поверхность
  обслуживания), либо raw-SQL агента (небезопасно/непредсказуемо).

## 1. Область v1 (подтверждено владельцем)

Tool-use работает ТОЛЬКО для двух shared-фич, и только если они реально
включены (`get_bot_features(bot_id)`) у конкретного бота:

- **sellable_items**: `create_sellable_item`, `update_sellable_item`,
  `set_sellable_item_active` (скрыть/показать — удаления позиций нет,
  сам `sellable_items.py` его не поддерживает).
- **payments**: `refund_payment` (только флаг статуса в БД — реального
  возврата денег через Telegram Payments API не существует).

Template-специфичные таблицы (туры, брони, заказы конкретного шаблона)
— вне v1. Бот без sellable_items/payments работает ровно как раньше
(chat-режим на Haiku, без инструментов).

## 2. Механизм

1. `on_group_message` теперь принимает `config` (duck-typed, `.db_path`)
   — тот же объект, что уже инжектится в `sellable_items`/`payments`
   хендлеры через `ConfigMiddleware` на общем `Dispatcher`; отдельного
   `get_bot()`-похода за db_path не понадобилось.
2. `enabled_features = get_bot_features(bot_id) ∩ {sellable_items, payments}`.
   Если пусто — старое поведение, Haiku, без `tools`.
3. Если не пусто — модель **Sonnet** (`claude-sonnet-5`, не Haiku:
   владелец подтвердил, что надёжность выбора инструмента важнее
   экономии), к system-промпту добавляется правило "вызывай инструмент
   только при явной и однозначной просьбе, иначе отвечай текстом" плюс
   снимок текущих данных (`_build_tool_context`: список позиций
   каталога с id/ценой/активностью, последние 20 платежей с
   charge_id/суммой/статусом) — чтобы Claude мог сослаться на id/charge_id
   из СПИСКА, а не выдумывать.
4. Ответ Claude либо `text` (как раньше), либо ОДИН `tool_use` блок.

## 3. Подтверждение — ничего не пишется без ✅

`tool_use` НИКОГДА не исполняется сразу. `_describe_tool_call()` строит
человекочитаемое превью ("➕ Добавить позицию «Экскурсия», цена 500₽"),
сохраняется в `_pending_actions[bot_id]` (token, tool_name, tool_input,
`created_at`) с TTL 5 минут, отправляется в группу с кнопками
✅ Подтвердить / ❌ Отменить (`gt_ok:<token>` / `gt_no:<token>`).

`cb_grouptask_confirm`/`cb_grouptask_cancel` — новые callback-хендлеры
на том же `router`:
- Только `OWNER_ID` (`_is_owner`), только из УЖЕ привязанной группы
  (`get_group_task_config`) — те же гейты, что у `on_group_message`.
- Токен должен совпасть с последним предложенным — устаревший/чужой
  callback молча отклоняется (`show_alert`, без записи).
- `_pending_actions.pop(bot_id)` происходит СРАЗУ после сравнения токена,
  до первого `await` — защита от двойного тапа/повторной доставки
  callback от Telegram: без этого два почти одновременных ✅ могли бы
  оба пройти проверку токена до того, как один из них снимет запись
  (event loop переключается на первом `await`), и `create_sellable_item`
  (не идемпотентен, в отличие от `refund_payment`/
  `set_sellable_item_active`) создал бы позицию дважды.
- Просроченный (>5 мин) pending — отклоняется, не исполняется.
- Исполнение — ТОЛЬКО через `_execute_tool_call()`, который заново
  строго валидирует `tool_input` (длины полей, диапазон цены,
  существование `item_id`) и вызывает CRUD-функцию нужного feature-модуля
  напрямую — никакого raw SQL из `group_task.py`.
- `❌` отменяет без записи.

## 4. Ограничения OWNER_ID / rate-limit

Не изменились: `on_group_message`'s `OWNER_ID`-гейт и
`_RATE_LIMIT_SECONDS` (1 запрос/3 сек) остаются как есть и покрывают
ВХОД в tool-use ветку так же, как раньше покрывали chat-ветку. Кнопки
подтверждения дополнительно гейтятся `_is_owner` + group-binding
независимо (не полагаются только на то, что сообщение уже прошло
Haiku/Sonnet-ветку).

## 5. Явно НЕ в этой итерации

- Произвольный SQL / генерация схемы на лету.
- Template-специфичные таблицы — потребует ручных tool-схем по каждому
  шаблону отдельно, отдельная будущая работа.
- Несколько tool_call за одно сообщение — одно ТЗ = максимум одно
  предлагаемое действие.
- Жёсткое удаление позиций (`sellable_items.py` не предоставляет такой
  операции вообще, только скрытие).
