# Шаблон «Агрегатор каналов» — инвентаризация и дизайн (СТОП перед кодом)

## 1. Что уже готово в features/channel_monitor.py + runtime/userbot_worker.py

Работающий фундамент — это FSM-обвязка над Telethon-юзерботом плюс фоновый воркер:

- **Авторизация юзербота**: risk-ack → телефон → код → (опц.) 2FA-пароль,
  с cooldown/FloodWait-защитой, session_string шифруется (Fernet,
  `USERBOT_ENCRYPTION_KEY`), хранится per-bot в `userbot_sessions`.
- **Подключение каналов**: ввод `@username` → юзербот резолвит и
  джойнится → строка в `monitored_channels` (bot_id, username, channel_id,
  title, active-флаг с toggle-кнопкой).
- **Приём постов**: `runtime/userbot_worker.py` держит один живой
  Telethon-клиент на bot_id, слушает `NewMessage` от подключённых каналов,
  пишет сырой `text` в `channel_posts` (bot_id ⇢ monitored_channel_id ⇢ post).
- **Summary**: отдельный фоновый цикл (`_summarize_loop`, интервал
  `SUMMARIZE_INTERVAL_SECONDS`) берёт посты с `summary IS NULL`, прогоняет
  через `services/gemini_service.summarize_post` (один текстовый summary на
  пост, без схемы полей) и пишет обратно.
- **Лента**: `/monitor` → «📰 Лента» — последние 15 постов (`FEED_LIMIT`),
  просто summary/текст построчно, без фильтров и без экспорта.
- **Права**: все хендлеры под `_is_bot_admin` — только владелец бота видит
  что-либо (это фича для владельца, не публичный контент).
- **Отключение**: `/disconnect_monitor` — ревокация сессии.

Это ФИЧА поверх произвольного шаблона (`COMPATIBLE_WITH: *`), встраиваемая
через `bot_commands`. У неё нет своего `/start`, нет собственного онбординга
"какие данные собирать", нет расписания отчётов, нет структурированного
вывода — только сырой текст + один general-purpose summary.

## 2. Чего не хватает для полноценного самостоятельного шаблона

Чтобы это стало не "фичей, прикрученной к чужому боту", а отдельным
шаблоном `templates/channel_aggregator.py`, где мониторинг — это ГЛАВНАЯ и
единственная функция, нужно:

1. **Собственный `/start`** — представление бота ("Я собираю посты из
   каналов, которые вы укажете, и присылаю готовую сводку"), а не только
   `/monitor`-вход поверх чужого меню.
2. **Настройка "что извлекать" (структура данных)** — сейчас Gemini делает
   один и тот же общий summary для всех постов независимо от канала и цели.
   Нужен способ владельцу бота задать *схему* (например: для канала вакансий
   — «зарплата, локация, требования»; для канала новостей — «главная суть в
   1 предложении + тема»). Без этого "структурирует в таблицу" из ТЗ не
   выполняется — сейчас это просто текстовый пересказ, а не таблица полей.
3. **Табличный/строчный вывод, а не лента текстом** — отчёт должен быть
   готовым к использованию (таблица/список с колонками), а не потоком
   HTML-абзацев в Telegram-сообщении.
4. **Готовый отчёт по расписанию** — сейчас есть только "по запросу"
   (кнопка «Лента»). Нужен дайджест-планировщик (ежедневно/еженедельно) с
   доставкой владельцу, аналогично cron-паттернам других шаблонов
   (`reminders`/`staff_scheduler` и т.п. — фоновый `asyncio`-таск с
   периодом, отправка `bot.send_message`).
5. **Экспорт готового отчёта** — сейчас нет выгрузки: ни в Google
   Sheets (`features/sheets_links` / `office_events` уже дают паттерн
   интеграции), ни в файл (CSV/xlsx через `openpyxl`, как в
   `sales_analytics.py`/`templates`). "Отдаёт в готовом виде" предполагает
   пользователю не только сообщение в Telegram, но и файл или таблицу.
6. **Более одного получателя отчёта?** — сейчас всё завязано на
   `_is_bot_admin` (владелец = единственный получатель). Нужно решить,
   остаётся ли это так в шаблоне (вероятно да, для MVP) или есть подписчики.
7. **Управление "шумом"** — сейчас нет фильтрации по ключевым словам/
   релевантности, каждый пост из подключённого канала попадает в ленту.
   Агрегатор без фильтра на большом канале за неделю даст нечитаемую простыню.
8. **Ограничение числа каналов/постов** — нет квоты в шаблоне (в отличие от
   фичи, где это чей-то один из многих модулей, шаблон как отдельный продукт
   вероятно должен ограничивать число каналов per bot и объём истории).

## 3. Дизайн шаблона (для обсуждения, БЕЗ кода)

### 3.1 Онбординг (что отслеживать + что извлекать)

`/start` → приветствие → тот же risk-ack + авторизация юзербота (переиспользуем
FSM `channel_monitor.py` как есть — он уже per-bot и надёжен) → далее НОВЫЙ шаг:

**Добавление канала с профилем извлечения**, на канал:
1. `@username` канала (как сейчас).
2. Выбор шаблона схемы полей — 3–4 готовых пресета кнопками, чтобы не
   заставлять владельца писать промпт с нуля:
   - «Вакансии» → поля: должность, зарплата, локация, контакт
   - «Новости/анонсы» → поля: заголовок, дата, ключевые темы, суть в 1 фразе
   - «Объявления/лоты» → поля: товар, цена, контакт
   - «Аналитика/охваты» → поля: заголовок, дата, ключевые темы, метрики
     вовлечённости (просмотры/реакции/репосты — то, что отдаёт Telethon по
     сообщению: `views`, `forwards`, счётчик реакций; не требует отдельного
     Gemini-вызова, это сырые метаданные поста, кладутся при приёме, а не
     при summarization)
   - «Свободная схема» → владелец текстом перечисляет поля, например
     "цена, срок, площадь" — это просто список названий колонок,
     передаётся в промпт Gemini как инструкция извлечения.
   Схема хранится как JSON-список названий полей в `monitored_channels`
   (новая колонка `extract_schema`), per канал, а не глобально на бота —
   разные каналы разного назначения нормально сосуществуют в одном боте.
   Поля "заголовок/дата/метрики вовлечённости" не требуют LLM — заголовок
   можно эвристически взять как первую строку поста, дата уже есть в
   `channel_posts.posted_at`, метрики — из `views`/`forwards` события
   Telethon (сейчас `runtime/userbot_worker.py` их не сохраняет — это
   отдельное дополнение схемы `channel_posts`, а не LLM-задача). Только
   "ключевые темы" и произвольные пользовательские поля идут через Gemini.

### 3.2 Извлечение (замена/расширение summarize_post)

Вместо одного `summary`, для каналов со схемой — structured extraction:
Gemini вызывается с list полей → возвращает JSON `{field: value, ...}` →
кладётся в новую колонку `channel_posts.extracted` (JSON text) вместо/вместе
с `summary`. Канал без схемы (пресет "Свободная схема" пропущен) — старое
поведение: свободный summary как fallback.

### 3.3 Ограничение доступа: юзербот видит только те каналы, где сам состоит

**Это ключевое, неустранимое ограничение Telegram Client API, не баг фабрики.**
`on_channel_username_entered` (features/channel_monitor.py:592-656) уже
реализует это на практике: юзербот-аккаунт при добавлении канала обязан
сам зайти в него (`JoinChannelRequest`) — публичный канал он вступает
автоматически по `@username`, но:

- **Закрытый (приватный) канал** — юзербот НЕ МОЖЕТ вступить сам по
  username, только по инвайт-ссылке или если его туда добавил
  администратор. Сейчас это уже возвращает явную ошибку
  (`ChannelPrivateError` → "🔒 Этот канал закрытый — мониторинг возможен
  только если ваш аккаунт уже состоит в нём или получит приглашение
  отдельно"), т.е. база для объяснения пользователю уже есть в коде фичи.
- **Закрытый чат/супергруппа** — то же самое, плюс для чтения истории
  сообщений (не только новых) юзерботу нужно быть участником УЖЕ ДО
  того, как сообщения были отправлены — Telegram не даёт истории до
  момента вступления для непубличных чатов.
- **Публичные каналы** работают "из коробки" через текущий флоу
  (auto-join по `@username`), это основной путь для MVP — большинство
  запрашиваемых кейсов (новости, вакансии, объявления) публичные.

**Как объяснить это пользователю в самом шаблоне** (не просто ошибка
в моменте, а проактивный онбординг-гайд):
1. На экране добавления канала — короткая заметка прямо в тексте:
   "Работает автоматически для публичных каналов (просто @username).
   Для закрытых каналов/чатов ваш аккаунт должен быть уже приглашён в
   них — бот сам вступить в закрытый канал не может (ограничение
   Telegram), либо сгенерируйте инвайт-ссылку в самом канале-источнике
   и пришлите её при добавлении".
2. Отдельный пункт FAQ/гайд, доступный кнопкой из главного меню
   («❓ Как добавить закрытый канал») — пошагово: как автор канала
   добавляет ваш аккаунт-юзербот вручную (по номеру телефона/username),
   либо как получить и переслать инвайт-ссылку боту, чтобы он мог
   вступить по приглашению (`ImportChatInviteRequest` — сейчас не
   реализовано, канал для расширения на будущее, не MVP).
3. `RISK_TEXT` уже описывает риски аккаунта, но не описывает это
   ограничение доступа — стоит либо дополнить его отдельным абзацем, либо
   показывать это отдельным сообщением на шаге "Добавить канал" (второе
   лучше — ограничение релевантно именно в момент добавления, не в
   момент авторизации).

Итог для MVP: auto-join по `@username` для публичных остаётся как есть;
для закрытых — явное сообщение с инструкцией "перешлите инвайт-ссылку
или попросите добавить ваш аккаунт вручную", без автоматического
вступления по инвайту (это отдельная, более рискованная функциональность
с точки зрения ToS Telegram — вступление по невалидной/чужой ссылке).

### 3.4 Получение отчёта

Два режима, оба нужны (совпадает с ТЗ "по расписанию, по запросу"):

- **По запросу**: кнопка «📊 Отчёт» — вместо текущей ленты абзацами,
  рендерит табличное сообщение (моноширинный текст либо — предпочтительно —
  CSV/xlsx-файл, отправляемый как документ; Telegram-сообщение плохо
  читается как таблица при >5 строках). Возможность выбрать период
  (сегодня/неделя/всё) и канал (все/один).
- **По расписанию**: настройка в меню — "присылать сводку каждый день в
  HH:MM" или "раз в неделю по дню недели" (аналог существующих
  cron-подобных фоновых тасков в других шаблонах). Фоновый `asyncio`-таск
  с проверкой раз в минуту (как `reminders`), при срабатывании — тот же
  файл/сообщение, что и по кнопке «Отчёт», но за период с прошлой отправки.
- **Оба канала доставки одновременно** (Google Sheets-таблица как живой,
  постоянно обновляемый источник + периодическая Telegram-сводка как
  push-уведомление) — соответствует формулировке ТЗ "таблица в Google
  Sheets... или периодическая сводка в Telegram, или и то и другое": Sheets
  синхронизируется при каждой новой extraction (через существующую
  `sheets`-фичу, см. 3.5), а Telegram-сводка — по расписанию/по запросу
  поверх тех же данных. Обе доставки не исключают друг друга.

### 3.5 Экспорт

Минимум для MVP: генерация `.csv` "на лету" (без внешних сервисов,
`csv`+`io.StringIO` → `BufferedInputFile`, паттерн уже есть в
`sales_analytics.py`/`orders_tracker.py` для выгрузок).

Google Sheets — владелец явно назвал это одним из целевых форматов отчёта
("таблица в Google Sheets"), поэтому в отличие от прошлой версии дизайна
это не откладывается за MVP, а идёт вторым каналом доставки: интеграция
через уже существующую sheets-фичу (см. `link_context.py`/office-routing
дизайн из предыдущих сессий) — при появлении новой extraction строка
дописывается в закреплённый Google-лист владельца, колонки = поля схемы
канала (`extract_schema`). CSV остаётся как способ "разовой" выгрузки по
кнопке без необходимости иметь подключённые Sheets.

### 3.6 Ограничения / анти-шум

- Лимит каналов на бота (например 10) — защита от квоты Telegram/FloodWait
  на общий юзербот-аккаунт (риск уже описан в `RISK_TEXT`).
- Опциональный keyword-фильтр per канал (список слов, "не показывать посты
  без слова X") — снижает шум для активных каналов. Может быть отложено
  за MVP.
- Хранение истории постов: TTL/лимит (например 30 дней) — иначе `channel_posts`
  растёт неограниченно на free-run боте.

## 4. Открытые вопросы владельцу

1. Экспорт отчёта: Google Sheets + CSV-файл (по кнопке) — оба сразу, как
   описано в 3.5? Или для MVP оставить только один канал доставки, а
   второй добавить позже?
2. Пресеты схем полей — четыре предложенных (вакансии/новости/объявления/
   аналитика с метриками вовлечённости) — ok, или другой набор ближе к
   реальным сценариям использования?
2а. Закрытые каналы (3.3): для MVP достаточно текстовой инструкции
   "перешлите инвайт-ссылку автору/попросите добавить аккаунт вручную",
   или сразу нужен автоматический join по инвайт-ссылке
   (`ImportChatInviteRequest`, доп. риск с точки зрения ToS)?
3. Расписание отчёта: свободный ввод времени/дня, или фиксированные
   пресеты («каждое утро в 9:00», «раз в неделю по понедельникам»)?
4. Лимит каналов на бота — 10 достаточно, или нужно больше/настраиваемо?
5. Оставляем ли переиспользование `features/channel_monitor.py` как есть
   (шаблон просто ЕСТЬ этот модуль + свой `/start`), или нужен
   самостоятельный форк логики под шаблон (например другая FSM-структура
   ради схем полей)? Рекомендация: переиспользовать модуль как есть и
   расширить (schema per channel, report generation) — не дублировать
   auth/join-логику, она уже прошла security-ревью.

Жду решения владельца по этим пунктам, дизайн не финализирован, кода нет.
