Critical Исправлено сразу features/payments.py:268

on_successful_payment падал с AttributeError на 19 из 23 payments-совместимых шаблонов

PaymentsConfig (протокол) утверждает, что у каждого совместимого шаблона Config несёт поле bot_id — это неверно. Реальная проверка всех templates/*.py нашла поле bot_id только в 4 из 23: car_rental, course_tracker, event_rsvp, orders_tracker. У остальных 19 (в т.ч. shop_catalog, moderator, booking_*, accountant — самые вероятные кандидаты для 3 тестовых ботов) поля нет вовсе.

Сценарий отказа Клиент оплачивает реальный платёж → строка платежа корректно записывается в БД → сразу после коммита обращение к config.bot_id кидает необработанный AttributeError → в вебхук-режиме это долетает до owner как критический алерт "unhandled_exception" на каждый успешный платёж. Деньги не теряются, но первый же реальный платёж в тестовой сессии выглядел бы как «платежи сломаны».
Исправлено: заменено на getattr(config, "bot_id", None) — деньги записываются как и раньше, событие order.created для «офисов» просто не публикуется там, где bot_id недоступен (как и было задумано изначально). Тесты (77 шт., payments/sellable_items/narrow_risk_review) — зелёные.

AssemblyAI SDK опрашивается синхронно в default executor-потоке без asyncio.wait_for. Try/except ловит исключение, но не зависание. При зависании поллинга статус «🎤 Распознаю...» висит бесконечно, поток из пула теряется навсегда — повторные зависания постепенно исчерпывают пул потоков процесса.

Сценарий отказаСетевой затык на стороне AssemblyAI при обработке голосового сообщения в /create → пользователь ждёт вечно, поток утекает.

Major Требует отдельного ТЗ handlers/create_bot.py:1158, 1265

Файл сгенерированного бота именуется по bot_name (от Claude), а не по уникальному bot_id

extract_bot_name() ничем не гарантирует уникальность (snake_case, ≤20 символов) — вполне вероятны совпадения (shop, booking, orders) у двух разных пользователей. Второй бот с таким же именем молча перезаписывает .py-файл первого на диске. Оба они уже сохранят в БД одинаковый file_path. Первый бот не падает сразу (код уже загружен в его процессе), но следующий /admin/reload или рестарт подгрузит код второго бота в процесс первого — тихая подмена логики между двумя клиентами. То же с аватарками (ниже критичности — теряется только картинка).

Сценарий отказаДва клиента создают ботов с похожими названиями почти одновременно → у одного из них бот через время начинает вести себя как бот другого клиента, без единой ошибки в логах.
Рекомендация: ключевать файл по bot_id, а не по имени (имя оставить только как отображаемую метку) — не одна строка, т.к. файл пишется до того, как bot_id известен (round-trip с BotFather происходит между этими шагами). Нужно дизайн-решение.
Major Требует отдельного ТЗ handlers/create_bot.py:1234-1237

Нет проверки на дубликат токена перед созданием записи бота

Валидация токена при ручном вводе — только ":" in token and len(token) >= 30. Поиска по существующим ботам с тем же токеном нет, колонка bots.token в БД без UNIQUE. Сценарий отказаВладелец или клиент случайно вставляет токен уже зарегистрированного бота → один из двух ботов перестаёт отвечать без какого-либо алерта.
Рекомендация: проверка на существующий токен перед вставкой + отказ/предупреждение.

Minor На заметку runtime/miniapp_api.py:435-459, 395-410

role_filter с default_deny: False полностью отключает admin-gate как страховку

_admin_gate_ok считает ресурс безопасным при одном лишь наличии ключа role_filter, независимо от формы. Если у роли-резолвед фильтра явно стоит default_deny: False и у пользователя нет ни одной из объявленных ролей — фильтр возвращает пустой where (не фильтровано), а admin-gate это не перепроверяет. Итог: гипотетически любой аутентифицированный пользователь бота увидел бы все строки ресурса.

СценарийСейчас не эксплуатируется: оба живых шаблона с role_filter (team_manager, habit_tracker) используют либо ownership-only форму, либо явный default_deny: True; AI-генератор miniapp_config вообще не знает о role_filter. Риск актуален только если человек вручную допишет role_filter с default_deny: False в новом шаблоне.
Рекомендация: не давать default_deny: False для роли-резолвед фильтров, либо перепроверять admin-статус в этом случае явно.
Minor На заметку runtime/miniapp_api.py:624-641

Ownership-контроль при создании записи покрывает только простую форму where

_resolve_create_owner_column форсирует owner-колонку только когда where матчит ровно "<col> = :telegram_user_id". Для любой другой формы (subquery, join) — ownership при создании не форсируется вовсе.

СценарийНе эксплуатируется сейчас: во всех текущих шаблонах creatable: False на уровне ресурса для всех role_filter-ресурсов. Актуализируется в момент, когда появится первый role-scoped + creatable ресурс.

Проверено и подтверждено рабочим корректно

  • SQL-инъекции: все имена таблиц/колонок в miniapp_api.py и factory_analytics_api.py берутся из доверенного, провалидированного miniapp_config — никогда из тела запроса; значения всегда параметризованы.
