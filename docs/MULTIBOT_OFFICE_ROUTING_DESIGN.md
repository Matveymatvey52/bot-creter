# Этап E: мультибот/офис-роутинг в /create — дизайн

Статус: ЧЕРНОВИК, СТОП перед реализацией. Ждёт решения владельца.

## 1. Что уже есть (факты из кода)

- `/create` сейчас — линейный одноботовый пайплайн: `handlers/create_bot.py`'s
  `CreateBotStates.gathering` → `chat_gather_requirements()` (services/claude_service.py:1373,
  system-промпт `GATHER_SYSTEM_PROMPT`) крутит диалог, пока не увидит маркер
  `===READY_TO_GENERATE===`, затем весь текст после маркера — это `bot_summary`,
  **один** блок текста, который идёт в `generate_bot_code()` и превращается в
  **один** файл `templates/*.py` или from-scratch генерацию. Структура `_pending`
  (create_bot.py:634) и вся цепочка `waiting_for_display_name` →
  `waiting_for_welcome_photo` → `waiting_for_avatar_photo` → `waiting_for_token`
  жёстко рассчитаны на ОДИН создаваемый бот за проход.
- Офисная инфраструктура для связи между существующими ботами уже реализована и
  в master (`docs/OFFICES_DESIGN.md`, влито 5bc77fb): `db.database.bot_office_links`
  (source_bot_id, target_bot_id, event_type), `features/office_events.py::publish_event()`,
  закрытый набор типов событий (`OrderCreatedEvent`, `TaskAssignedEvent`), и
  UI-визард для владельца — ручное связывание ПОСЛЕ того, как оба бота уже
  созданы (`handlers/manage_bots.py`'s "🏢 Офисы" + miniapp-визард). Это
  **пост-фактум связывание существующих ботов**, не часть `/create`.
- "Цифровой офис" (boss_bot/manager_bot, отдельная память) уже использует
  `TaskAssignedEvent`/office_events как канал `voice_intake → office_events →
  reminders → miniapp` — то есть офисные связи между конкретными шаблонами уже
  осмысленный, работающий сценарий, просто настраиваемый вручную.

## 2. Что меняется: результат gathering — не всегда один бот

Сейчас `GATHER_SYSTEM_PROMPT` инструктирует Claude выдать РОВНО один
`===READY_TO_GENERATE===` блок с одним `bot_summary`. Задача — научить этот же
диалог распознавать, когда пользователь фактически описывает НЕСКОЛЬКО ботов
("хочу бота для заказов и отдельно бота для бухгалтерии, чтобы они
переговаривались") или явно просит "офис" (несколько связанных ботов + связи
между ними за один заход), и выдать не один summary, а СТРУКТУРУ.

### 2.1 Формат вывода gathering (предлагается)

Вместо одного текстового блока после `===READY_TO_GENERATE===`, промпт просит
Claude выдать **JSON**, который парсится ОДНИМ способом для обоих случаев
(single и multi), чтобы не плодить две ветки формата:

```json
{
  "bots": [
    {"role_hint": "orders", "summary": "..."},
    {"role_hint": "accounting", "summary": "..."}
  ],
  "links": [
    {"source_role_hint": "orders", "target_role_hint": "accounting", "event_type": "order.created"}
  ]
}
```

- Один бот — `"bots"` с одним элементом, `"links": []`. Это гарантирует, что
  весь текущий одноботовый путь (`extract_bot_name`, `generate_bot_code`,
  `_pending`, весь `waiting_for_*` хвост) продолжает работать почти без
  изменений: `bots[0].summary` == нынешний `bot_summary`.
- `role_hint` — короткий человеческий тег ("orders", "accounting"), не имя
  бота — имя всё ещё генерирует `extract_bot_name()` отдельно на каждый
  `summary`. Нужен, чтобы `links` могли ссылаться на ещё-не-созданных ботов
  (у которых нет `bot_id`, пока BotFather не выдал токен).
- `event_type` — ОБЯЗАН быть одним из уже существующих `_EVENT_TYPES` в
  `features/office_events.py` (`order.created`, `task.assigned`, …) — LLM не
  придумывает новый тип на лету, тот же принцип "закрытый список", что уже
  задокументирован в office_events.py:54-63. Если запрошенная связь не
  ложится ни в один существующий тип — Claude обязан явно сказать
  пользователю, что такая связь пока не поддерживается, а не выдумать
  произвольный event_type.

### 2.2 Изменения в GATHER_SYSTEM_PROMPT

- Добавить раздел, объясняющий модели закрытый список `event_type` (нужно
  прокинуть в промпт актуальный список из `_EVENT_TYPES` — то есть
  `chat_gather_requirements()` должен либо импортировать этот список и
  подставлять его в system-промпт динамически, либо промпт держит статичную
  копию, которую нужно вручную синхронизировать при добавлении нового типа
  события — рекомендация: динамическая подстановка, чтобы не рассинхронизировать
  вручную).
- Явно указать: если пользователь описывает больше одного бота, но НЕ просит
  их связать — всё равно можно вернуть несколько `bots` с пустым `links`,
  это просто пакетное создание нескольких независимых ботов (сценарий "хочу
  бота для магазина И бота для доставки, они не связаны").
- Вопросы уточнения (1-2 за раз, как сейчас) должны при необходимости
  спросить, ЧТО именно должно быть связано и как: "Бот-заказы должен
  сообщать боту-бухгалтерии о каждом новом заказе?" — то есть Claude сам
  предлагает конкретный `event_type` из списка и спрашивает подтверждение,
  а не молча решает.

## 3. Изменения в пайплайне после gathering

### 3.1 `_process_gathering_text` (handlers/create_bot.py)

- Парсинг ответа: вместо `response.split("===READY_TO_GENERATE===")` + весь
  хвост как один `summary`, парсим JSON из хвоста. Если `json.loads` падает —
  трактовать как одноботовый legacy-формат (обратная совместимость на время
  миграции промпта, если он иногда всё ещё выдаёт голый текст) ИЛИ жёстко
  требовать от промпта всегда JSON — решение зависит от того, насколько
  надёжно Claude Haiku держит формат под давлением диалога (нужно проверить
  эмпирически перед реализацией, не гадать).
- `bots` длины 1 с пустыми `links` → существующий путь один-в-один, без
  визуальных отличий для пользователя.
- `bots` длины >1 ИЛИ непустые `links` → новая ветка: нужен новый набор
  FSM-состояний, потому что весь хвост диалога (`waiting_for_display_name`
  → … → `waiting_for_token`) должен повториться **на каждого бота из
  списка**, последовательно, а не один раз.

### 3.2 Новый FSM-контур для мультибот-режима

Ключевой архитектурный вопрос: `_pending[user_id]` сейчас — это ОДНА запись
на пользователя (create_bot.py:634), потому что `auto_launch_managed_bot()`
дожидается ОДНОГО callback от BotFather-фичи (managed bot creation) и по
`creator_user_id` находит ровно одну ожидающую генерацию. Для нескольких
ботов подряд это не подходит as-is — нужно либо:

- **(A) Последовательная очередь.** `_pending[user_id]` становится списком/
  очередью; `auto_launch_managed_bot()` всегда обрабатывает ГОЛОВУ очереди,
  и после успешного запуска бота — если очередь не пуста — автоматически
  запускает `_run_generation` для следующего элемента и заново показывает
  кнопку "Создать бота ✨" для BotFather. Пользователь проходит весь цикл
  (BotFather → токен → авто-запуск) N раз подряд, для каждого бота из
  списка. Минимальные изменения к текущей модели, но N раз то же самое
  трение для владельца.
- **(B) Общий "офисный" contextID.** Ввести `office_session_id` (UUID),
  под которым складывается весь список `bots`+`links`, и функция, которая
  после того как ВСЕ N ботов реально созданы (есть настоящие `bot_id`),
  одним проходом вызывает `add_office_link()` (db/database.py:1030) для
  каждого элемента `links`, подставляя `role_hint → bot_id` по факту
  создания. Требует надёжного отслеживания "все ли боты офиса уже
  созданы" — по сути свой мини-стейт-машина поверх существующей FSM
  очереди из варианта A.
- Рекомендация: (A) как основа доставки (владелец физически должен пройти
  BotFather N раз — это ограничение Telegram API, не архитектуры), + (B)
  как надстройка для авто-простановки office-связей в конце, вместо того
  чтобы заставлять владельца вручную идти в "🏢 Офисы" UI после.

### 3.3 Стыковка с `bot_office_links`

- После того как последний бот из `office_session_id` создан и получил
  `bot_id` (в `auto_launch_managed_bot()`, там же где сейчас разово
  вызывается `create_bot_record_with_admins`), для каждого элемента
  `links` резолвим `role_hint` → `bot_id` (просто dict, накопленный по
  ходу очереди) и вызываем существующий `db.database.add_office_link()`
  — **никакого нового кода на стороне office_events.py не нужно**, вся
  инфраструктура связей уже есть, /create просто становится ещё одним
  вызывающим кроме ручного miniapp-визарда.
- Открытый вопрос: что если БОТ №2 из офиса генерируется, а BotFather-шаг
  для него владелец отменяет/бросает на середине (`/cancel`)? Нужна явная
  политика — либо весь `office_session_id` считается сорванным (остальные
  боты из очереди тоже не создаются), либо уже созданные боты остаются, а
  недостающие связи просто не создаются (частичный офис). Рекомендация:
  частичный офис — отменять уже созданные боты немыслимо (они реальные
  Telegram-боты с токенами), значит откат невозможен по конструкции, только
  "создать что успели, связи только между реально созданными".

## 4. Открытые вопросы к владельцу (СТОП здесь)

1. **UX цикла N ботов**: подтверждаете вариант (A) — пользователь вручную
   проходит BotFather для КАЖДОГО бота из офиса по очереди (Telegram не даёт
   способа создать несколько ботов одним действием), с понятным прогресс-
   индикатором ("Бот 1 из 3: заказы")? Альтернатив в рамках Bot API нет.
2. **Формат вывода gathering — JSON**: ок ли переводить `GATHER_SYSTEM_PROMPT`
   на структурированный JSON-вывод вместо текущего plain-text summary? Это
   меняет промпт, который, возможно, всё ещё дорабатывается в параллельной
   сессии (этапы A/B/C) — нужно свериться с её финальной версией
   `GATHER_SYSTEM_PROMPT` перед реализацией этого этапа, чтобы не переписать
   друг друга.
3. **Расширение event_type на лету**: если пользователь просит связь, для
   которой в `_EVENT_TYPES` нет подходящего типа — Claude должен (а) сказать
   "пока не поддерживается, вот что есть" и продолжить без этой связи, или
   (б) это повод завести новый `event_type` как отдельную ручную доработку
   (не автоматизировать генерацию новых dataclass-типов событий через LLM —
   рискованно по тем же причинам, что и остальной "закрытый список"
   дизайн office_events.py). Рекомендация: (а).
4. **Приоритет**: это отдельная, некороткая задача (новый FSM-контур,
   очередь, промпт-миграция, обвязка с office_links) — подтверждаете, что
   это следующий этап работы, а не что-то, что нужно уместить в тот же
   прогон, что и этап D?
