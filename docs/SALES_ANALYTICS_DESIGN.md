# Per-bot Sales Analytics — Design (Stop Point, No Code Yet)

Scope: a feature module giving a bot **owner** stats about *their own bot's*
business data (bookings/orders/appointments — whatever the host template
tracks), surfaced inside that bot's mini-app. Not to be confused with
`runtime/factory_analytics_api.py`, which is the factory owner's cross-bot
dashboard reading the central `bots`/`bot_feedback` tables — this module never
touches that.

## 1. What already exists that this builds on

- **Feature-modules convention** (`features/*.py`, `runtime/registry.py`):
  a file with a `# FEATURE:` / `# COMPATIBLE_WITH:` header, a module-level
  `router`, optional `init_db(db_path)`. `registry.py` clones the router per
  bot and runs `init_db` against the *host template's own* SQLite file —
  features never own a separate DB. `payments.py` is the reference shape.
- **`miniapp_config`** (`db/database.py` table `bot_miniapp_config`,
  generated by `services/claude_service.py::_generate_miniapp_config`):
  a declarative `{"resources": [{"name","table","order_by","fields":[...]}]}`
  schema, validated against the template's real `CREATE TABLE` statements.
  Served generically by `runtime/miniapp_api.py`, rendered generically by the
  single shared SPA in `miniapp/` (`ListScreen`/`DetailScreen`/etc., driven
  purely by the JSON — no per-bot frontend code).
- **`office_hook_config`** (same storage pattern, `db/database.py` +
  `services/claude_service.py::_generate_office_hook_config`): a tiny
  Haiku-generated hint `{"table": str, "match_field": str|None}` naming which
  table + column holds the customer's Telegram chat_id. This is the existing
  precedent for "know one thing about a table's semantics without knowing the
  domain" — exactly what repeat-customer analytics needs.

## 2. Config: reuse office_hook_config, don't invent a third generator

Rather than a new Haiku generation step, **reuse `office_hook_config`** as
the "which table/column is the primary business record + who's the customer"
hint. It already exists per bot (generated at bot-creation time), already
gives `{table, match_field}`. Analytics needs one more piece: **which column
is the record's timestamp**, for time-bucketing.

Proposal: extend `office_hook_config`'s generation prompt (in
`_generate_office_hook_config`) to also emit `created_at_field` (nullable) —
the column holding row-creation time, validated the same way (regex-checked
against real columns, discarded to `null` on mismatch, degrading gracefully:
if absent, the "records over time" chart just isn't offered).

This avoids: a fourth Haiku call, a fourth config table, a fourth generation
prompt to maintain, and keeps one config doing double duty (office hooks +
analytics) since both need the same "what table, whose chat_id" facts.

If office_hook_config is null/absent for a bot (some templates have no
customer-facing record, e.g. `moderator`), the analytics feature module is
simply not offered — `COMPATIBLE_WITH` lists only templates where
`office_hook_config` generation is expected to succeed (a subset overlapping
heavily with `payments`' own whitelist).

## 3. Generic metrics computable with just `{table, match_field, created_at_field}`

All computed with raw SQL against the host template's own db_path, no domain
knowledge required:

1. **Volume over time** — `COUNT(*) GROUP BY date(created_at_field)`,
   bucketed day/week/month by requested period (reuse
   `templates/sales_analytics.py`'s `_get_period_sql` period-bucketing logic
   as a style reference, not its table).
2. **Period-over-period delta** — this week vs last week count, simple % diff.
3. **Top repeat customers** — `COUNT(*) GROUP BY match_field ORDER BY COUNT DESC
   LIMIT N`, joined against Telegram chat_id → display name if available
   (best-effort; falls back to raw chat_id).
4. **New vs returning** — per period, count of `match_field` values seen for
   the first time vs seen before.
5. **Total record count** (all-time and current period) — simplest possible
   metric, works even if `created_at_field` is missing.

Nothing here needs to know if a "record" is a booking, an order, or an
appointment — that's the same abstraction `office_events` already leans on
(a generic "something happened" record keyed by customer chat_id).

Explicitly **out of scope for v1**: revenue/amount aggregation. That would
require a third schema hint (`amount_field`) plus currency handling and is
meaningfully harder to keep domain-agnostic (not every template's "amount"
means the same thing, refunds complicate sums). Flag as a possible v2 if the
owner asks for it later — don't build it speculatively now.

## 4. Feature module shape

`features/sales_analytics.py`, following `payments.py`'s pattern:

- No new tables of its own (unlike payments, which adds a `payments` table —
  analytics is pure read-over-existing-data, so `init_db` is a no-op or
  absent entirely).
- No Telegram-side router commands needed for the *data* — the whole point
  is this lives in the mini-app, not as bot chat commands. The module's
  `router` can be empty/omitted if nothing needs registering, OR (per the
  user's owner button-UI convention) expose a single `/analytics` button /
  deep-link that opens the mini-app directly to the analytics screen, mirror
  of how other owner-only screens are surfaced today.
- Exposes computation functions (e.g. `compute_metrics(db_path, config,
  period)`) that `runtime/miniapp_api.py` calls, not registered as aiogram
  handlers — this is API-layer logic, same as how `miniapp_api.py` already
  reads `miniapp_config` directly without going through a feature router.

## 5. API surface

New read-only endpoint in `runtime/miniapp_api.py`, owner-authenticated the
same way existing miniapp endpoints are:

```
GET /api/{bot_id}/analytics?period=week|month|quarter
```

Returns `{volume: [{date, count}], delta_pct, top_customers: [{match_field,
count, display_name?}], new_vs_returning: {new, returning}, total}`.
Returns 404/empty-capability if the bot has no usable `office_hook_config`
(feature not applicable) — SPA hides the analytics section in that case,
same graceful-degradation pattern miniapp_config already uses when Haiku
generation fails validation.

## 6. Mini-app UI

New section in the **existing shared SPA** (`miniapp/`), not a new app:

- A new screen type alongside `ListScreen`/`DetailScreen`, e.g.
  `AnalyticsScreen`, added to the schema normalization
  (`lib/displaySchema.ts`) as a synthetic resource-like entry the SPA shows
  only when the backend reports analytics capability (from step 5's
  404-or-not check on load, mirroring how `bot_id=0` is special-cased today
  for `FactoryDashboardScreen`).
- Charts: period selector (week/month/quarter tabs) → line/bar chart for
  volume-over-time, a simple horizontal bar list for top customers, and two
  stat tiles (total, delta %). Keep it to 2-3 chart types — this is a small
  owner-facing dashboard, not a BI tool. Use whatever charting approach the
  SPA's existing dependencies support (check `miniapp/package.json` before
  picking a library — avoid adding a new dependency if something chart-
  capable is already there).
- Entry point: an "Аналитика" nav item/button visible only to the bot owner
  (existing owner-detection pattern in the SPA, same as create/edit
  affordances already restricted to owner).
