## 1. Главный вывод

**Telegram-сторона держит контекст правильно. Мини-апп не знает слова «родитель» вообще.**

Ожидалось, что чинить придётся 41 шаблон по отдельности. Это не так. Боты в
Telegram работают корректно: у них есть активный родитель, фильтрация по нему
и его имя в заголовке. Тот самый ДДС, который вы открыли, в Telegram выглядит
образцово.

Сломан ровно один слой — обобщённый движок мини-аппа, через который те же
таблицы показываются повторно. В нём понятия «родитель» нет ни в запросе, ни в
контракте `miniapp_config`, ни в интерфейсе. Поэтому дефект и тиражируется:
каждый новый бот автоматически получает исправную Telegram-часть и сломанную
мини-апп-часть.

### Один и тот же ДДС в двух местах

**Telegram — верно** (`templates/tour_operator.py:1224`, `_section_summary`):

```
💰 ДДС — Сочи

⬆️ Приход:  420 000 ₽
⬇️ Расход:  318 500 ₽
📊 Баланс:  101 500 ₽
```

Родитель назван. Записи и итоги — по `tour_id` через
`cashflow_get_totals(db_path, parent_id=tid)`.
(Суммы в примере синтетические.)

**Мини-апп — сломано:**

```
ДДС
ДДС · 5 операций

— чей тур, не сказано
— строки всех туров вперемешку
— итогов нет вовсе
```

Родителя нет ни в заголовке, ни в запросе, ни в схеме.

## 2. Где именно ломается

Три точки, все — в общем движке, ни одной в бизнес-логике шаблонов.

### 2.1. Запрос не умеет фильтровать по родителю

`runtime/miniapp_api.py:494`, `list_resource_handler`:

```python
sql = f"SELECT id, {columns} FROM {resource['table']}"
params: tuple = ()
if role_clause is not None:
    where_sql, where_params = role_clause
    sql += f" WHERE {where_sql}"
    params = where_params
sql += f" ORDER BY {order_by} LIMIT 200"
```

Условие по родителю отсутствует, и передать его неоткуда — параметра
родителя в обработчике не существует. Любой SCOPED-раздел неизбежно
отдаёт записи всех родителей сразу.

### 2.2. Родителя негде объявить

Контракт `miniapp_config`. У ресурса есть `table`, `fields`, `order_by`,
`creatable`, `title`, `titleField`, `role_filter` — и ни одного поля про
принадлежность. Даже там, где автор шаблона про родителя знает, он может
лишь показать сырую колонку: в `tour_operator` это поле с меткой
**«ID тура»**, которое пользователь вводит числом руками.

### 2.3. Заголовку нечего показать

`miniapp/src/screens/ListScreen.tsx`, шапка списка:

```tsx
<ScreenHeader eyebrow={resource.title} title={resource.title} ... />
```

Заголовок — это `resource.title`, то есть буквально слово «ДДС». Данных
о родителе на экране нет, потому что API их не присылает. Итогов по выборке
экран не считает ни для одного раздела.

### 2.4. Telegram-часть шаблонов — чинить нечего

Проверены выборки SCOPED-таблиц во всех 41 шаблоне. Подтверждённых
находок — одна, и та спорная (см. §6.5). Списки фильтруются по родителю,
агрегаты считаются по нему же, имя родителя стоит в заголовке.
Автоматическая эвристика дала около сотни срабатываний — все ложные.

Эталон для подражания — `templates/accountant.py:672-690`: выборка
`WHERE project_id=? AND tx_date BETWEEN ? AND ?`, заголовок
`📊 Отчёт: {project['name']} — {label}`.

## 3. Различение, без которого аудит невозможен

ТЗ делит сущности надвое: SCOPED и GLOBAL. На реальных данных двух категорий
не хватило — **внешний ключ сам по себе ещё не означает принадлежность**.
Пришлось развести три случая, и именно это различение определяет, что чинить.

| Тип | Что это | Признак | Дефект? |
|---|---|---|---|
| **C — контейнер** | Родитель как вместилище | Список без родителя бессмыслен: «операции ДДС», «гости», «задачи проекта» | **Да, это и есть дефект** |
| **A — измерение** | Родитель как признак | Общий список осмыслен, родитель работает фильтром: «все расходы за месяц» | Нет, но тип объявить надо |
| **D — состав** | Строки внутри родителя | Отдельным списком не показываются никогда: `order_items`, `attachments` | Нет, контракт на будущее |

### Подтверждение из практики

В мокапе `design/mockups/miniapp_mockup_E.html` «Отели» были помечены как
общий справочник — и код попытался показать у них тур, которого нет. Это
ошибка ровно того же класса, допущенная тем, кто про неё знал.

В реальном `tour_operator` отели, наоборот, **привязаны** к туру через
`hotels.tour_id`. Без явного объявления типа угадывание не работает ни в
одну сторону.

## 6. Классификация находок

### 6.1. P0 — не найдено. Утечек между владельцами нет

Проверено отдельно, поскольку это безопасность, а не UX.

У каждого бота свой файл базы (`entry.config["db_path"]`), поэтому
межвладельческая утечка через мини-апп невозможна конструктивно. Внутри бота
доступ закрывают `_admin_gate_ok` (`miniapp_api.py:435`) и `role_filter` —
оба применяются и в списке (`:490`), и в карточке (`:537`). Обработчиков
UPDATE/DELETE в мини-аппе нет вовсе.

Ранее закрытые задачи по `role_filter` per-project scoping и multitenancy-аудиту
дублировать не нужно — новых мест того же класса не обнаружено.

### 6.2. P1 — мини-апп молча создаёт сироту в ДДС

`templates/tour_operator.py:260`:

```python
{"name": "parent_id", "label": "ID тура", "kind": "text",
 "list": False, "detail": False, "create": True},
```

Стоит `create: True`, но **не стоит `required`**. Сервер проверяет
обязательность честно (`miniapp_api.py:596`, `missing = required_fields - values.keys()`),
но для этого поля проверять нечего.

Запись, созданная без родителя, ложится в базу с пустым `parent_id` — и после
этого не видна ни в одном туре в Telegram, потому что там выборка идёт строго
по `parent_id=?`. Деньги внесены, деньги пропали.

У остальных разделов (`program`, `locations`, `hotels`, `guests`) `required`
проставлен, и сервер такую вставку отклоняет с 400.

### 6.3. P1 — обязательные поля не проверяются на клиенте

`miniapp/src/screens/CreateFormScreen.tsx:21`:

```tsx
const requiredFilled = resource.createFields.every(
  (f) => f.name !== 'name' || values.name?.trim()
)
```

Смотрит ровно на одно поле с именем `name` и игнорирует флаг `required`.
Кнопка «Создать» активна при незаполненном обязательном родителе, пользователь
жмёт и получает сырую ошибку 400 от сервера. Сервер контракт держит,
интерфейс — нет.

### 6.4. P2 — 29 разделов не говорят, чьи это записи

Исходный случай и основной объём работы. Данные при этом не просто «верные,
но непонятные» — они ещё и смешаны, поскольку фильтра нет вовсе. Формально это
ближе к P1, но чинится одной правкой движка, а не двадцатью девятью, поэтому
идёт единым блоком.

### 6.5. P2, спорный — поиск по всем поездкам, когда активной нет

`templates/trip_manager.py:1261`. Когда активная поездка не выбрана, поиск
сознательно идёт по всем и выдаёт «🔍 Найдено: N» без указания, из каких
поездок результаты. Ветка написана намеренно (есть явный `if trip: ... else: ...`),
поведение защитимое; не хватает только подписи.

Единственная находка на Telegram-стороне за весь аудит.

## 7. Честно о методе

ТЗ требует описать ограничения эвристики. Они существенные, и на них придётся
опираться при проектировании CI-проверки.

**Поиск родителя по имени колонки пропускает связи.** Правило «`x_id` → таблица
`x`/`xs`» не нашло `channel_posts.monitored_channel_id → monitored_channels` и
`rental_bookings.item_id → rental_items`. Обе связи найдены руками при сплошном
просмотре. Значит, CI-проверка **не может выводить родителя из имён** — его
придётся объявлять. Это прямо обосновывает этап D.

**Поиск незафильтрованных выборок регулярным выражением непригоден.** Около
сотни срабатываний на Telegram-стороне, ноль подтверждённых. Шум дают чтения
одной строки по `WHERE id=?` (законные) и обрывы длинных SQL-строк на границе
regex. Такой проверке в CI нужен либо разбор AST, либо статус предупреждения
без падения сборки — как уже сделано с мягкими предупреждениями в
`scripts/check_miniapp_drift.py`.

**Отнесение к C/A/D — суждение, а не вывод.** Каждый из 29 случаев разобран
вручную по тому, как раздел реально используется. Спорные места вынесены в §8.

## 8. Нужны решения владельца

ТЗ (§6 п.2) просит подтвердить спорную классификацию до массовых изменений.
Спорных мест три.

**1. Согласны ли вы с тем, что отнесено к «измерениям»?**
Товары по категории, расходы по категории, слоты по врачу, заказы по клиенту,
аренды по предмету оставлены общими списками с родителем-фильтром: «все расходы
за месяц» кажется осмысленным запросом. Если расходы всегда смотрятся внутри
категории, эти разделы переезжают в контейнеры и объём работ растёт примерно
на треть.

**2. Нужен ли режим «Все» со сводной колонкой?**
В варианте E он есть. Он полезен, но именно он породил ошибку с отелями, и он
же примерно удваивает работу над каждым разделом. Альтернатива — всегда
требовать выбранного родителя и не показывать сводно вообще.

**3. Что делать с уже существующими сиротами в ДДС?**
Данные не удаляем. Предлагается показать их отдельной группой «Не привязано» с
возможностью назначить тур вручную — молчаливая привязка «по дате к ближайшему
туру» угадывала бы и могла ошибиться в деньгах. Если такие записи в боевой базе
есть, их стоит посмотреть до правок.

## 9. План на этапы C и D

Поскольку источник один, порядок работ меняется против ТЗ: **сначала движок,
потом объявления в шаблонах**. Так 29 разделов чинятся одной правкой кода плюс
29 строками декларации.

1. **Поле `scope` в контракте ресурса.**
   `{"type": "scoped", "parent": "tours", "via": "tour_id", "label_field": "name"}`
   либо `{"type": "global"}`. Ресурс без объявления — ошибка валидации.

2. **Движок учит родителя.** `list_resource_handler` принимает `?parent=`,
   добавляет условие для SCOPED-ресурсов и возвращает имя родителя и итоги по
   выборке. `schema_handler` отдаёт объявление на клиент.

3. **Экран получает строку контекста.** Постоянная подпись «Раздел по туру ·
   Сочи» со сменой родителя, режим «Все» с колонкой-различителем, честная
   подпись у справочников. Логика — из варианта E, **стили — нет**: дизайн
   на согласовании, это отдельная задача.

4. **Создание спрашивает родителя.** Выбор из списка вместо ввода числа руками;
   `required` проверяется по флагу. Закрывает обе находки P1 (§6.2, §6.3).

5. **Проверка в `scripts/check_miniapp_drift.py`.** Готовая площадка: скрипт
   уже импортирует шаблоны, читает `CREATE TABLE` (в том числе из фич через
   `_tables_from_imported_features`) и делит severity на жёсткую и мягкую.
   Жёстко валим за отсутствие `scope` и за SCOPED без колонки родителя; мягко
   предупреждаем по эвристике выборок. **Обязательно проверить на намеренно
   сломанном примере** — иначе проверка бесполезна (критерий приёмки ТЗ).

6. **Правило в `CLAUDE.md` и в промпт генератора** (`services/claude_service.py`,
   `_generate_miniapp_config`), плюс пункт про scope-контракт в подходящего из
   существующих агентов-ревизоров в `.claude/agents/` — дополнить, а не плодить
   нового.

7. **Тесты.** На каждый починенный раздел: две записи разных родителей, список
   по A не содержит записи B, агрегат по A не включает суммы B.
