# ТЗ — Аудит и искоренение «безродных записей» (scope/context holes)

**Статус:** к исполнению в отдельной сессии
**Приоритет:** высокий — дефект системный, повторяется в каждом новом боте
**Создано:** 2026-08-21

---

## 1. Откуда взялась задача

При просмотре mini-app тур-оператора владелец открыл раздел «ДДС» и увидел таблицу операций, у которой **нигде не написано, к какому туру она относится**. Заголовок — просто «ДДС · 5 операций». У пользователя нет ответа на вопрос «это движение денег по какому именно туру?».

Это не косметика. Это класс дефекта, который тиражируется: генератор создаёт бота с несколькими сущностями, одна из них логически принадлежит другой (операции → тур, задачи → проект, замеры → объект, платежи → заказ), но эта принадлежность **не выражена ни в UI, ни в фильтрации, ни иногда даже в схеме БД**.

Цель работы: найти все такие места в существующих шаблонах/фичах, починить их и **закрыть возможность их появления в новых ботах**.

---

## 2. Определение дефекта

**«Безродная запись» (orphan-context)** — сущность логически принадлежит родительской сущности, но связь потеряна на одном из уровней:

| Уровень | Как выглядит дефект |
|---|---|
| Схема БД | нет `parent_id` / FK, связь «подразумевается» или хранится строкой-названием |
| Запрос | `SELECT * FROM ops` без `WHERE tour_id = ?` — записи всех родителей вперемешку |
| Создание | форма создаёт запись, не спрашивая и не проставляя родителя → сирота в БД |
| Список (UI) | не видно, чьи это записи; нет колонки-различителя при сводном показе |
| Экран/заголовок | нет постоянного индикатора «вы смотрите X по родителю Y» |
| Агрегаты | итоги/суммы/счётчики посчитаны по всей таблице, а не по текущему фильтру |
| Смешение типов | справочники и привязанные сущности выглядят и ведут себя одинаково |

### Ключевое различение, которое надо провести в каждом боте

Каждая сущность обязана быть отнесена к одному из двух типов:

- **SCOPED** — принадлежит родителю. Без указания родителя список бессмысленен.
  *Примеры: операции ДДС → тур; гости → тур; программа → тур; задачи → проект; замеры → объект.*
- **GLOBAL (справочник)** — общая для всех, живёт вне контекста родителя.
  *Примеры: отели, категории, прайс-лист, сотрудники.*

Дефект возникает ровно там, где это различение не сделано.

### Живой пример (уже реализован, брать за образец)

`design/mockups/miniapp_mockup_E.html` — эталонное решение:
- константа `SCOPED = ['program','lip','guests','dds']` — явный список привязанных разделов;
- переменная `ctx` — текущий родитель (`'sochi'`) либо `'all'` (сводно);
- `ctxbar(section)` — постоянная строка под шапкой: «Раздел по туру · Сочи», кликабельна, ведёт на экран выбора;
- для GLOBAL-разделов вместо неё честная подпись «Общий справочник — не зависит от тура»;
- фильтрация `inCtx()` + подпись под заголовком «Тур «Сочи» · записей: 5»;
- в сводном режиме (`ctx='all'`) в таблице **появляется колонка «Тур»**, иначе строки неразличимы;
- итоги (приход/расход/остаток) **пересчитываются от отфильтрованных строк**, а не захардкожены.

> При реализации этого мокапа сразу же был пойман баг именно этого класса: код попытался показать «тур» у справочника «Отели», у которого родителя нет. Это подтверждает — без явного разделения SCOPED/GLOBAL ошибка возникает даже у того, кто про неё знает.

## 3. Что нужно сделать

### Этап A. Инвентаризация (без него остальное вслепую)

1. Найти все шаблоны ботов и фич-модули. Отправные точки: `features/`, шаблоны ботов (~32 штуки), `runtime/miniapp_api.py`, `registry.py`, генератор `miniapp_config`. **Точные пути проверить самостоятельно — список не считать исчерпывающим.**
2. Для каждого шаблона выписать все сущности (таблицы/разделы) и проставить тип: **SCOPED** (с указанием родителя) или **GLOBAL**.
3. Результат — таблица в отчёте:

   | Шаблон | Сущность | Тип | Родитель | БД: есть FK? | Запросы: фильтруют? | UI: виден родитель? | Агрегаты: по фильтру? |
   |---|---|---|---|---|---|---|---|

4. Особое внимание шаблонам с несколькими связанными сущностями — там дефект почти гарантирован. По памяти проекта это как минимум: тур-оператор, `event_manager`, `shop_catalog`, `orders_tracker`, `repair_tracker`, `delivery_tracker`, `course_tracker`, `property_rental`, `expense_tracker`, `team_manager`, `coworking_space`, `booking_*`. Список проверить и дополнить.

### Этап B. Классификация находок

- **P0 — утечка данных между владельцами/проектами.** Запрос без фильтра по `owner_id` / `project_id`, из-за чего один клиент видит чужие записи. Это безопасность, а не UX. Чинить немедленно и отдельно.
- **P1 — функциональная ошибка.** Агрегаты считают лишнее; создание порождает сирот; список смешивает родителей без различителя.
- **P2 — потеря контекста в UI.** Данные верные, но пользователь не понимает, чьи они (исходный случай с ДДС).

> Про P0: в проекте уже были закрыты задачи по per-project scoping для `role_filter` и multitenancy-аудит. Проверить, не осталось ли аналогичных мест, и **не создавать дубликаты уже закрытых задач** — сверяться с git-историей.

### Этап C. Исправления

1. **БД:** добавить `parent_id` + индекс, если его нет. Миграция обратно совместимая; для существующих записей определить стратегию (backfill по косвенным признакам либо явная пометка «не привязано» с ручным разбором). Данные не удалять.
2. **Запросы:** все выборки SCOPED-сущностей обязаны фильтровать по родителю (и по владельцу, где применимо).
3. **Создание:** родитель проставляется явно. Если контекст неизвестен — сначала спросить родителя. Молча создавать сироту запрещено.
4. **UI бота:** в заголовке списка и в карточке всегда указывать родителя — строка вида `📁 Тур: Сочи` перед списком либо суффикс в каждой строке при сводном показе.
5. **UI mini-app:** постоянная строка контекста + смена родителя + режим «Все» с колонкой-различителем. Образец — вариант E.
6. **Агрегаты:** пересчитывать от текущей выборки. Захардкоженные итоги искать целенаправленно — это отдельная категория находок.

### Этап D. Профилактика — главная часть задачи

Починить существующее мало.

1. **Правило в инструкциях генерации.** Внести в `CLAUDE.md` и/или в промпт генератора шаблонов и генератора `miniapp_config`:

   > У каждой сущности бота должен быть явно объявлен тип: SCOPED (с указанием родительской сущности) или GLOBAL. Для SCOPED обязательны: колонка `parent_id` с индексом, фильтрация во всех выборках, указание родителя в заголовке списка и в карточке, пересчёт агрегатов по текущей выборке, запрос родителя при создании. Сущность без явно объявленного типа считается ошибкой генерации.

2. **Машиночитаемое объявление.** Ввести в описании шаблона / `miniapp_config` поле `scope: {type: "scoped", parent: "tours"}` либо `{type: "global"}`. Без него — падать на валидации. Это превращает правило из пожелания в проверяемый контракт.

3. **Автопроверка в CI** (по образцу существующего drift-check для `miniapp_config`). Валить сборку, если:
   - у сущности нет объявленного `scope`;
   - сущность объявлена SCOPED, но в схеме нет `parent_id`;
   - найдена выборка SCOPED-сущности без фильтра по родителю (эвристика по AST/regex допустима, но её ограничения описать честно);
   - у SCOPED-раздела в `miniapp_config` не задан источник контекста.

4. **Тесты.** На каждый починенный шаблон — регрессионный тест: две записи разных родителей; список по родителю A не содержит записи B; агрегат по A не включает суммы B.

5. **Чек-лист ревью.** Добавить пункт про scope-контракт в существующих агентов-ревизоров в `.claude/agents/` — дополнить подходящего, а не плодить нового.

## 5. Ограничения и что НЕ делать

- **Не менять дизайн mini-app.** Визуальные варианты в `design/mockups/` на согласовании у владельца — отдельная задача. Брать оттуда только логику контекста, не стили.
- **Не ломать существующих ботов.** Миграции обратно совместимые, данные не удалять.
- **Не переписывать шаблоны целиком** под предлогом аудита. Правки точечные, по найденным дефектам.
- **Не мержить в master без прогона тестов.** В репозитории часто работают параллельные сессии в разных worktree — перед мержем сверяться с актуальным master фактами (`git log`, `git status`), а не по памяти.
- **Не считать задачу выполненной, если CI-проверка не проверена на живом сломанном примере.**

## 6. Порядок работы

1. Этап A целиком, отчёт — до любых правок.
2. Показать владельцу таблицу инвентаризации и классификацию SCOPED/GLOBAL **до** массовых изменений: спорные случаи (что считать справочником) подтверждает он.
3. Затем P0 → P1 → P2.
4. Затем профилактика (этап D).
5. Финальный отчёт: что найдено, что починено, что осталось и почему.
