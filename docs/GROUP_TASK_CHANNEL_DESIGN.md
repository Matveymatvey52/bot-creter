# Групповой ТЗ-канал: владелец пишет боту задачу прямо в Telegram-группе

Статус: ЧЕРНОВИК, СТОП перед реализацией. Ждёт подтверждения владельца.
Продолжение `docs/OFFICES_DESIGN.md` — здесь только новая часть; вкладка
"Офисы" (bot↔bot связи через `office_events`) уже реализована в master и
не трогается этой задачей.

## 0. Что уже решено (из предыдущего обсуждения)

1. **office_events остаётся единственным bot↔bot транспортом.** Групповая
   Telegram-витрина для bot↔bot связей — опциональный read-only дайджест от
   Creator-бота, без добавления клиентских ботов в группу. Не часть этой
   задачи (уже реализовано/не запрошено отдельно).
2. **Групповой ТЗ-канал — отдельный, человек↔бот механизм.** Владелец
   создаёт СВОЮ Telegram-группу, добавляет туда реальных клиентских ботов,
   пишет им задачи через упоминание/reply, боты отвечают в группе.
3. **Область действия — ВСЕ боты фабрики**, не только from-scratch: единый
   переиспользуемый `features/group_task.py`-модуль (тот же паттерн, что
   `office_events.py`/`sheets.py` — `# FEATURE:`/`# COMPATIBLE_WITH:` заголовок,
   `router`, опциональный `init_db`), который любой шаблон подключает через
   `discover_features()`/`COMPATIBLE_WITH`, а from-scratch боты получают
   автоматически (как `office_events`/`sheets` сейчас).
4. **Privacy Mode: требовать Disable, с явным шагом в гайде.** Черновой
   пример в `GENERATE_SYSTEM_PROMPT` (`services/claude_service.py:259-296`)
   матчит упоминание по обычному тексту сообщения — это НЕ сработает, пока
   владелец не отключит Privacy Mode боту в BotFather (`/setprivacy` →
   `Disable`). Дизайн явно требует этого шага и объясняет его в UI, а не
   притворяется, что "просто работает" из коробки.

## 1. Существующий прецедент (для сверки, не для копирования как есть)

`services/claude_service.py:259-296` (`GROUP CHAT SUPPORT` в
`GENERATE_SYSTEM_PROMPT`) уже учит генератор кода писать для from-scratch
ботов:
- `GROUP_CHAT_ID` / `BOT_DISPLAY_NAME` — env-переменные на бота.
- `notify_group()` — сервер→группа уведомление.
- `handle_group_mention()` — фильтр `F.chat.type.in_({"group","supergroup"})`
  + `BOT_DISPLAY_NAME.lower() in text.lower()` + разовый вызов Haiku без
  памяти диалога, ответ через `message.reply()`.

Проблемы этого черновика, которые новый feature-модуль обязан закрыть:
- Разово генерируется как СЫРОЙ КОД внутри каждого from-scratch бота —
  нет для шаблонов (tour_operator, shop_catalog, ...) вообще, нет единой
  точки исправления бага/улучшения (пришлось бы регенерировать/патчить
  каждого бота отдельно, как `custom_features`).
  → Новый модуль решает: один `features/group_task.py`, доступный всем.
- Нет памяти диалога — каждое сообщение отвечается изолированно, без
  контекста предыдущих реплик той же "задачи" в группе.
  → Решается коротким scrollback-контекстом (см. §3).
- Нет привязки `group_chat_id` к конкретному `bot_id` в БД — жёстко в
  одну ENV-переменную на бота, не управляется через UI фабрики.
  → Новая таблица `bot_group_task_config` (см. §4).
- Молчаливо предполагает Privacy Mode уже выключен — нет проверки, нет
  диагностики "почему бот не отвечает".
  → UI-гайд подключения явно проговаривает шаг + подсказка "бот не
    отвечает? проверь Privacy Mode" в тексте самого экрана.

## 2. Архитектура: feature-модуль `features/group_task.py`

Копирует структурную конвенцию `office_events.py`/`sheets.py`:

```
# FEATURE: group_task
# COMPATIBLE_WITH: <все текущие 27 шаблонов>
```
- **Нет `init_db` в БД бота** — как `sheets.py`, состояние (привязанный
  `group_chat_id`) живёт в центральной `bots.db`, не в per-bot файле:
  это метаданные владельца о боте, а не данные самого бота.
- **`router`** — один `@router.message(F.chat.type.in_({"group",
  "supergroup"}))` хендлер, зарегистрированный через
  `_load_and_include_features()` (существующий by-convention путь, тот же
  что уже подключает `office_events`/`sheets`/`payments` каждому боту).
- Функция диспетчеризации отвечает ТОЛЬКО если апдейт — упоминание
  (`@bot_username` в тексте/entities) или reply на сообщение самого бота
  — то есть ровно то, что доходит до бота даже теоретически без Privacy
  Mode off через явную адресацию, но НА ПРАКТИКЕ Privacy Mode ON вообще
  не пересылает боту такие сообщения, если бот не админ группы — отсюда
  требование Disable Privacy (см. §0.4), а не просто "правильный фильтр".
- **Изоляция по `bot_group_task_config`**: хендлер срабатывает, только
  если `chat.id` сообщения совпадает с `group_chat_id`, сохранённым для
  ЭТОГО `bot_id` — предотвращает случайный отклик, если владелец забыл
  бота в старой/чужой группе (тот же принцип, что `_attach_bot_id_middleware`
  не даёт данным одного бота течь в другого).

## 3. Диалоговый слой — что отвечает боту

Не переиспользует `services/claude_service.py`'s `client` напрямую как
общий диалоговый движок (тот заточен под флоу создания бота — system-
промпты про генерацию кода). Новый, отдельный, лёгкий system-промпт:

- Модель: Haiku (дёшево, задача — короткий чат-ответ на ТЗ, не генерация
  кода) — тот же выбор, что уже в черновом промпт-примере.
- **Контекст**: последние N (например, 6) сообщений ИЗ ЭТОЙ группы,
  адресованных этому боту (mention/reply к нему), не весь groupchat —
  чтобы владелец мог дать составное ТЗ в 2-3 репликах, а не только
  одной фразой. Хранится в памяти процесса (как остальной MVP-слой
  `office_events` — no persistence через рестарт, приемлемо для чата).
- **Что бот "знает" о себе**: имя бота, `bot_type`/шаблон (из `bots`
  таблицы) — минимальный системный промпт "Ты — {name}, бот для {тип
  бизнеса}. Владелец даёт тебе задачу в рабочей группе, ответь по
  существу на русском." Никакого доступа к произвольным данным бота
  (SQL и т.п.) в первой итерации — это чат, не агент с tool-use; если
  понадобится "бот выполняет задачу, а не просто отвечает текстом" —
  отдельная, более поздняя итерация с явным набором tool'ов.
- **Кто может писать боту в группе** — только `OWNER_ID` (владелец
  фабрики). Любой другой участник группы, даже упомянувший бота,
  игнорируется — иначе группа становится открытым интерфейсом к
  Anthropic API за счёт владельца для любого, кто в неё попал.

## 4. Хранение: `bot_group_task_config`

Новая таблица в центральной `bots.db` (`db/database.py`, рядом с
`bot_office_hook_config`/`bot_sheets_config`):

```
CREATE TABLE IF NOT EXISTS bot_group_task_config (
    bot_id          INTEGER PRIMARY KEY REFERENCES bots(id) ON DELETE CASCADE,
    group_chat_id   INTEGER NOT NULL,
    enabled         INTEGER NOT NULL DEFAULT 1,
    created_at      TEXT DEFAULT (datetime('now','localtime'))
)
```
- `PRIMARY KEY(bot_id)` — один бот привязан максимум к одной группе за
  раз (проще для первой итерации; несколько групп на бота — не
  запрошено, не заводим).
- `group_chat_id` заполняется НЕ вручную владельцем (он не знает
  числовой ID новой группы) — см. флоу подключения §5: определяется
  автоматически из первого апдейта, когда бот добавлен в группу.

## 5. UX-флоу подключения — "явный гайд" (пункт 3 исходного вопроса)

Кнопка на панели бота (`handlers/manage_bots.py`, рядом с "🏢 Офисы"):

```
💬 Рабочая группа   callback_data=f"grouptask:{bot_id}"
```

### Экран "Рабочая группа" для бота X (`grouptask:{bot_id}`), ДО подключения
Текст объясняет, ЧТО произойдёт (пункт 3 вопроса — "что произойдёт после
подключения"), не просто кнопка:

> 💬 **Рабочая группа для {X}**
>
> Подключи бота к своей Telegram-группе — сможешь писать ему задачи
> прямо там (`@{X_username} сделай то-то` или ответом на его сообщение),
> и он будет отвечать в группе. Отвечает только тебе (владельцу), другие
> участники группы бота не получат ответа.
>
> **Как подключить:**
> 1. Создай новую Telegram-группу (или используй существующую).
> 2. Добавь туда бота **@{X_username}**.
> 3. Зайди в BotFather → выбери **@{X_username}** → **Bot Settings** →
>    **Group Privacy** → **Turn off**. *(Без этого шага бот не увидит
>    твои сообщения в группе, даже если упомянуть его по имени.)*
> 4. Напиши в группе что угодно, упомянув бота — фабрика подхватит
>    группу автоматически.
>
> [◀ Назад]

Кнопки: только "◀ Назад" — нет "Готово"/"Продолжить", потому что
подключение подтверждается автоматически (шаг 6 ниже), не вручную.

### Автоматическое обнаружение подключения
- `features/group_task.py`'s router слушает **любой** апдейт из группы,
  где бот упомянут/это reply на него, у которого ЕЩЁ НЕТ строки в
  `bot_group_task_config` для этого `bot_id`.
- Первый такой апдейт: записывает `(bot_id, chat.id)` в
  `bot_group_task_config`, отвечает в группу подтверждением:
  > ✅ Готово! Теперь пиши мне сюда задачи, упоминая @{X_username} или
  > отвечая на мои сообщения.
- Последующие апдейты из этой же группы обрабатываются как обычный ТЗ
  (см. §3), без повторного "подключения".
- **Ловушка, которую нужно явно предотвратить**: если владелец забыл
  выключить Privacy Mode (шаг 3 гайда пропущен), эта авто-регистрация
  ВООБЩЕ НЕ СРАБОТАЕТ (апдейт до бота не дойдёт), и владелец не поймёт
  почему — экран "Рабочая группа" ДО подключения должен явно предупредить
  об этом заранее (сделано текстом выше), а не полагаться на ошибку
  постфактум, которую некому будет показать.

### Экран "Рабочая группа" ПОСЛЕ подключения (`grouptask:{bot_id}`)
> 💬 **Рабочая группа для {X}**
>
> Подключено к группе «{group_title, если удалось получить через
> `get_chat`}».
>
> [🔌 Отключить]  [◀ Назад]

"Отключить" — `DELETE FROM bot_group_task_config WHERE bot_id=?`,
владелец может позже переподключить к другой группе тем же авто-флоу.

## 6. Риски и границы первой итерации

- **Стоимость**: каждое сообщение в группе, адресованное боту → один
  вызов Haiku. Владелец — единственный, кто может писать (см. §3),
  так что риск неконтролируемого расхода ограничен одним человеком;
  но всё ещё стоит поставить простой rate-limit (например, не чаще
  1 запроса в 3 секунды на бота) на случай случайного спама/двойного
  сообщения — тот же паттерн, что `_CRITICAL_ERROR_RATE_LIMIT_SECONDS`
  в `office_events.py`.
- **Несколько ботов в одной группе** — это ПОДДЕРЖИВАЕТСЯ естественно:
  каждый бот матчит только собственные упоминания/reply-на-себя, так
  что можно добавить 5 ботов в одну группу и адресовать задачи каждому
  по отдельности, обращаясь по имени — ровно то, что просил владелец.
- **Privacy Mode как постоянное требование эксплуатации, не разовая
  настройка** — если владелец когда-нибудь пересоздаст бота через
  BotFather (новый токен) без сохранения этой настройки, канал молча
  перестанет работать. Не решается в первой итерации (нет способа
  прочитать текущее значение Privacy Mode через Bot API), только
  фиксируется как известное ограничение.
- **Не агент, а чат** — бот не выполняет ТЗ автоматически (не создаёт
  записи в своей БД, не дёргает свои хендлеры) в первой итерации,
  только осмысленно отвечает текстом. "ТЗ" в данной итерации означает
  "разговор с ботом о задаче", не "бот сам исполняет задачу". Явно
  проговорить это владельцу перед реализацией — если ожидание было
  "бот реально что-то сделает по инструкции в группе", это другая,
  более сложная фича (tool-use агент поверх собственных хендлеров
  бота), не описанная здесь.
